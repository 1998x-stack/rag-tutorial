INDEXING / SCALE

高级索引架构：
从平面索引到多层与多索引

向量检索的精度不只取决于嵌入模型，也取决于“在多大的集合里找”。把所有文档放进一个平面索引，规模一大就会出现跨领域误召回、语言混杂、旧版本淹没新版本。这一篇讲清层级索引、多索引路由、更新策略与多租户隔离。

MECHANISM / PROBLEM

平面索引的局限

第五章讲分块、第六章讲嵌入时，都默认所有分块进同一个索引。在中小规模下这没问题，但一个常见的误解是“只要嵌入模型够好，一个平面索引就能支撑任意规模”。规模一上来，这个假设就会破。

用一个构造的例子说明。一家公司的知识库覆盖多个业务线、多种语言、多个版本：

  • 跨领域误召回：技术团队问“发布流程”，因为“招聘流程”和“发布流程”描述用词相近，HR 文档会被排到前面。
  • 语言混杂：中英文文档共处一个索引，一句中文查询可能召回英文片段，拼出语言不一致的上下文。
  • 旧版本洼没新版：“合同模板”与“标准合同”语义太近，已过期的模板与最新版被当成同一回事。
检索精度 = 嵌入质量 × 搜索空间大小与隔离。模型再强，也挡不住“在一个过大的、混杂的集合里排序”。把搜索空间先缩小、把不相关的领域先隔离，是索引层能直接做的事——这与换模型无关。

这一篇先讲“把搜索空间变小”（层级索引），再讲“把不同种类分给不同索引”（多索引路由），最后是更新与隔离。

MECHANISM / HIERARCHY

层级索引：逐层缩小范围

平面索引把“召回”变成了一次全局排序：要在一整套分块里找最相近的。层级索引换个做法：先建一层更粗的摘要，检索时先从粗层定位到范围，再逐层下钻到具体分块。搜索空间一层层变小，最后一层的排序就在更小、更相关的集合里进行。

RAPTOR（Sarthi 等，2024）是这种树状索引的一个代表方法：把文本分块后递归地聚类、为每个簇生成摘要，形成一棵自下而上的摘要树，检索时可以在不同层上取回。它与上一章 GraphRAG 的社区摘要有相似的“先聚再摘”思路，只是一个建在分块层次上，一个建在实体关系图上。

层级是拿构建成本换检索质量。每一层摘要都要额外生成与存储，且文档更新时摘要可能失效。层数不是越多越好，要按“文档量 × 查询里全局问题的比例”来权衡。

MECHANISM / ROUTING

多索引共存与路由

真实系统很少只有一个索引。第八章的 BM25（关键词精确）、第六章的向量（语义）、第二十章的知识图谱（关系）、以及时间范围索引，各自服务不同需求。一个路由器负责把查询分发给最合适的索引。

下面用一个确定性的玩具路由器把“分发 + 合并”走一遍。它用关键词规则选索引，再用 RRF 合并排名（RRF 在第十章已经推导过）：

# 玩具多索引路由：规则匹配 + RRF 合并（纯标准库）
INDEXES = {
    "keyword": lambda q: any(k in q for k in ("编号", "版本", "ID")),
    "time":    lambda q: any(k in q for k in ("最近", "2025", "本季")),
    "vector":  lambda q: True,  # 语义召回作为兵底
}
HITS = {"keyword": ["doc_v2"], "time": ["doc_q3"],
        "vector": ["doc_guide", "doc_v2"]}
K = 60

def rrf(lists):
    score = {}
    for docs in lists:
        for rank, d in enumerate(docs, start=1):
            score[d] = score.get(d, 0.0) + 1.0 / (K + rank)
    return sorted(score, key=lambda d: (-score[d], d))

q = "2025 年发布的 API 版本编号是什么？"
active = [name for name, match in INDEXES.items() if match(q)]
merged = rrf([HITS[name] for name in active])
print("激活索引:", active)
print("合并排序:", merged)
# 预期输出：
# 激活索引: ['keyword', 'time', 'vector']
# 合并排序: ['doc_v2', 'doc_guide', 'doc_q3']

运行条件：Python 3.10+，无第三方依赖、无网络。INDEXES 是写死的规则，HITS 是人为指定的命中，不是任何真实索引的输出；它只能证明“分发与 RRF 合并”的控制流。

按规则激活索引，并用 RRF 合并各路命中。
不同索引的分数不能直接相加。BM25 的分数与余弦相似度量纲不同，直接比较会得到错误排序。要么用 RRF 只靠名次，要么先把分数归一化到可比口径——这一点在第十章已经详细讨论。

MECHANISM / UPDATE

增量更新与定期重建

生产索引必须能更新。两种极端各有利弊：

策略做法优点局限
增量更新新文档到达时只计算它的嵌入并追加快、资源低、数据新鲜删除常是标记删除；长期碎片化，召回质量下降
定期全量重建定期对全部文档重算并重建索引无碎片、口径统一贵、耗时；重建期间新旧版本要切换
实时更新文档入库立即可检索适合新闻 / 监控类场景需索引结构支持动态插入（如 HNSW）

大多数生产系统采用“增量为主、定期重建”：平时用增量保证新鲜度，定期（例如每周）全量重建一次以清理碎片。第七章讲过，HNSW 支持动态插入，但删除通常是标记删除，图结构不会立即修好——这也正是需要定期重建的原因之一。

“实时”不是默认目标。实时更新带来更高的写入与一致性成本；只有当业务真的需要秒级可见时才值得。大多数知识库场景，分钟级到小时级的延迟已经够用。

MECHANISM / MULTI-TENANCY

多租户索引隔离

多租户 SaaS 场景下，索引层也要做隔离。第十七章讲的是权限层面的访问控制，这里讲的是索引层面的三种常见做法：

架构做法隔离性资源效率
每租户独立索引每个租户一套索引实例最好最低（N 租户 = N 套）
共享索引 + 租户字段过滤所有分块带 tenant_id，检索时过滤中（依赖过滤正确）高
混合大客户独立索引、小客户共享好高

共享索引要特别注意：过滤必须在检索内部完成（先按 tenant_id 限定候选），而不是检索完再在应用层剔除——后者会把其他租户的数据也拉进候选集，既有性能问题也是隔离风险。

MECHANISM / FRONTIER

让检索从失败中学习

一个静态索引建好之后不会再变：某个查询总是检不到好文档，它也不会自己调整。一个自然的想法是让索引/检索器从失败反馈里学习。常见的几条机制：

  • 失败捕获：当用户对结果不满意（显式“无用”或隐式追问/否定）时，把它记录下来，并尽量记下“用户当时想要什么”。
  • 微调检索器：对于反复失败的查询-文档对，用对比学习微调编码器，使正确的文档离查询更近。REPLUG（Shi 等，2023）就是用语言模型的反馈来训练检索器的一个例子。
  • 元数据增强：如果调整嵌入不足以解决，自动补充或修正文档的元数据标签（同义词、领域标签），让过滤与检索更精准。
  • 结构调整：更激进时，根据查询模式重建局部索引结构（例如把常被一起访问的文档放到相近的分区）。
“失败”的定义很难，本身就是一个坑。用户说“没用”不代表检索错了——也可能是生成阶段没用好了召回的上下文。如果不把失败归因到具体环节，直接去调检索器，就会把生成阶段的问题写成检索器的错。因此这一步仍应回到第十八章的多维评估上。

另外两个工程风险也需记住：增量微调可能造成灾难性遗忘（修好 A 类查询、眝坏了 B 类）；索引结构重组可能引起服务中断，需设计在线切换。这些机制更适合先当作研究方向，而不是直接上生产。

把“自适应”当成工程约束，而不是宣称。原站页面里“斯坦福大学 2025 年提出自校正索引”“头部向量数据库厂商 2025–2026 路线图”“预计 12–18 个月落地”等表述无法核实，本页已删除。能确认的是：用反馈微调检索器是已有方法（如 REPLUG）；其余属于工程探索。
