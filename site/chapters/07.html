RETRIEVAL / INDEX

向量索引：
HNSW、IVF 与近似的代价

上一篇把文本变成了向量，这一篇要回答：当库里有一百万条向量、每次查询只有几十毫秒预算时，系统如何既找得到大概率正确的近邻，又不扫描全部数据。

暴力扫描的算账图与分桶的直觉召回率定义纯 Python 实验

MECHANISM / COST

一百万个向量要比较多少次？

假设知识库有 n 个分块向量。用户提问时，系统要找出与查询向量最接近的前 k 个。最直接的做法叫暴力搜索（brute-force / flat 检索）：把查询向量与库里每一个向量都算一次相似度，再排序取前 k。它保证找到精确的最近邻，代价是每次查询都要触碰全部 n 条数据。

规模 n每次查询的向量比较次数触碰全部数据的比例
1 万104100%
100 万106100%
1 亿108100%

真正的耗时还要乘以向量维度 d 和单次浮点乘加的机器速度。举例说明：若 n=106、d=768，一次查询约需 7.68×108 次乘加；在后面给出的 Python 玩具测量里，这已经超出毫秒级预算。这是教学示意：真实延迟取决于硬件、向量维度、是否使用 SIMD/GPU 与批处理，不能把这里的量级当作某产品的基准。

问题重述。“精确地算完所有向量”与“在线服务的延迟预算”是冲突的。向量索引要做的，是让我们只比较一小部分向量，同时尽量不丢掉真正相关的证据。

MECHANISM / APPROXIMATION

近似检索：用误差换延迟

近似最近邻（Approximate Nearest Neighbor，ANN）索引主动放弃“一定找到精确最近邻”的保证，换取“只访问一小部分数据”。它输出一个候选集合，再在候选内排序取前 k。只要真正相关的向量以很高概率落在候选里，检索质量就不会明显下降——这正是 RAG 检索可以接受的取舍，因为后续还有重排与生成环节。

于是出现了两个必须同时监控的量：延迟（latency）与召回率（recall）。所有“加了向量库就快 100 倍”这类说法，都必须标明是在哪个数据集、哪个召回目标下的测量。ANN 索引不是免费的午餐，下面的图和实验都围绕这条取舍曲线展开。

MECHANISM / GRAPH

HNSW：分层小世界图导航

HNSW（Hierarchical Navigable Small World）把向量组织成一张分层图。它并不是把向量排成树，而是让每个节点与若干个近邻相连：上层节点稀疏、连线长，像“跳大区域”的快线；越往下层节点越密，可以精细定位。查询从最顶层的一个入口点开始，在每一层用贪心搜索向更近的邻居移动，找到局部最近的点后降到下一层继续，直到最底层。

这套结构来自 Malkov 与 Yashunin 的原始 HNSW 论文，其核心主张是：在图上做贪心与多入口搜索，可以获得对数级别的期望搜索复杂度，并在多个基准上接近精确检索的召回。论文里的具体召回与速度数字绑定于当时的数据集与参数，不能直接当作任何库上任意配置的性能承诺。

参数（常见命名）作用调大的代价
M / max_connections每个节点保留的邻居数召回上升，内存与建索引时间上升
efConstruction建索引时的候选宽度图更连通，但构建更慢
efSearch查询时的候选宽度召回上升，单次查询变慢

关键工程点：efSearch 可以在查询时临时调大而不必重建索引，因此常用它来调节“召回—延迟”曲线。这些参数的默认值因库而异，选型时要以自己的数据实测，而不是照搬某个教程的常数。

MECHANISM / BUCKETS

IVF 与 PQ：分桶与压缩

IVF（Inverted File Index）走的是另一条路：先用 k-means 把全部向量聚成 nlist 个簇，每个簇记下中心点；然后把每个向量分配到最近的簇，形成一组倒排列表。查询时，先只把查询与 nlist 个中心比一遍，选出最近的 nprobe 个簇，只扫描这些簇里的向量。这样就把“访问全部数据”换成了“访问少数几个簇”。

扫得少自然可能漏掉真近邻：若目标向量恰好落在未被选中的簇里，就会漏检。nprobe 越大，覆盖越多，召回越高、延迟越差。这是与 HNSW 同构的一一取舍，只是控制旋钮不同。

PQ：把向量压缩成短码

当向量数量或维度太大、连存储都成了瓶颈时，乘积量化（Product Quantization，PQ）把每个高维向量切成 m 段，每段各自用一个小的码本量化成一个短编码。检索时不再存完整浮点向量，而是用查表近似计算距离。代价是量化误差：重建出的距离是近似值，排序可能与精确距离不一致。（PQ 见 Jégou 等人 2011，FAISS 把 IVF 与 PQ 组合成大规模方案，见 Johnson 等人 2017。）

索引内存召回构建速度典型取舍
Flat（暴力）高（存全部向量）精确无需训练精确但慢，适合小库
IVF中高取决于 nlist/nprobe需先聚类内存友好、构建快
IVF + PQ低有量化损失需训练码本省内存，精度下降
HNSW高通常较高较慢召回—速度平衡好

上表是定性的工程经验总结，不是某篇论文的基准表；具体排序必须用自己数据集的召回—延迟曲线来验证。

MECHANISM / METRIC

召回率与候选集的形式定义

为了测量 ANN 丢了什么，需要一个参照。设查询 q 的精确前 k 近邻集合为 Nk(q)：用同一距离函数、暴力比较全部向量得到的前 k 个最近邻；用 Rk(q) 表示某个 ANN 索引实际返回的前 k 个结果。则 ANN 的召回率定义为两者交集占精确结果的比例：

Recall@k=|Nk(q)∩Rk(q)|k

两个集合都按同一个距离函数、同一套向量与同一模型版本定义，分母是 k。它衡量的是“索引把多少个真近邻找回来了”；若同时关心位置质量，还需要 nDCG 等排序指标。请注意：召回率是相对精确暴力结果而言的，而业务上真正关心的是否检索到能回答问题的证据，两者不是同一个集合（分块与嵌入质量会先在更前面引入误差）。

不要混用口径。“召回 0.95”必须说清是相对哪套精确结果、k 取多少、距离函数是点积还是余弦、向量是否归一化、模型与索引版本是什么。否则不同来源的召回数字不可比。

MECHANISM / LIFECYCLE

建索引、更新与元数据过滤

向量索引不是“建一次就完”的静态物。参数（如 HNSW 的 M、IVF 的 nlist）在建索引时确定，图上结构也随之固定；后续新增向量可以插入，但删除往往先记为墓碑（tombstone），真正的空间回收与结构优化需要重建或合并。因此向量库的“删除了就一定释放内存”不能默认成立，需要在评测里验证。

操作常见做法必须验证
新增增量插入索引插入后召回是否下降；是否需要定期重建
删除 / 撤权墓碑标记或过滤条件旧向量是否真的不可见、空间是否回收
重建后台重建并原子切换版本切换期间查询一致性与回滚路径
模型升级用新模型重嵌并全量重建新旧向量不可混放在同一索引比较

元数据过滤：先过滤还是后过滤

RAG 往往要按租户、版本、时间等字段过滤。若先让索引返回前 k 再在结果里丢掉不满足条件的，当符合条件的向量很少时，前 k 可能几乎没有命中，召回骤降；而在检索引擎内做前置过滤（pre-filtering）能保证只在不违反过滤条件的子集里搜索，但需要引擎支持带过滤的图/倒排遍历，否则可能退化成扫描。这两种策略的差异必须在带过滤条件的查询集上单独测。

模型与索引版本绑定。不同嵌入模型、不同归一化方式产生的向量不在同一个表示空间。升级嵌入模型时，必须对全库重新编码并重建索引，不能把新查询向量拿去与旧文档向量直接比距离。

MECHANISM / EXPERIMENT

不依赖库的召回实验

下例只用 Python 标准库，用二维点代替高维向量：先用暴力搜索得到精确前 k，再拿一个“玩具 IVF”——用随机质心分桶、只扫描最近的 nprobe 个桶——去比较。它要验证的不变量是：nprobe 越小，扫描的向量越少，召回率可能下降；本例中四档召回均为 1.00。这是教学示意，不是任何向量库的实现，也不代表高维空间中的真实数值。

import random, math
random.seed(7)
DIMS, N, K = 2, 400, 5
data = [[random.gauss(0, 1) for _ in range(DIMS)] for _ in range(N)]
query = [random.gauss(0, 1) for _ in range(DIMS)]

def d2(a, b):
    return sum((x - y) ** 2 for x, y in zip(a, b))

exact = set(sorted(range(N), key=lambda i: d2(query, data[i]))[:K])

NLIST = 8
centroids = random.sample(data, NLIST)
buckets = {c: [] for c in range(NLIST)}
for i, v in enumerate(data):
    c = min(range(NLIST), key=lambda j: d2(v, centroids[j]))
    buckets[c].append(i)

def ann(nprobe):
    order = sorted(range(NLIST), key=lambda j: d2(query, centroids[j]))
    scanned = [i for j in order[:nprobe] for i in buckets[j]]
    return set(sorted(scanned, key=lambda i: d2(query, data[i]))[:K]), len(scanned)

for nprobe in (1, 2, 4, 8):
    hits, scanned = ann(nprobe)
    recall = len(hits & exact) / K
    print(f"nprobe={nprobe}  扫描={scanned:>3}/{N}  recall@{K}={recall:.2f}")
# 预期：nprobe 增大时扫描量上升，recall 单调不降（单次运行不一定严格单调）。

运行条件：Python 3.10+，无第三方依赖、无网络。由于质心是随机抽取的、数据是低维的，不同随机种子或维度会得到不同数字；例子的作用是展示扫描量随 nprobe 变化，而召回可能已饱和，而不是提供一个可用索引。真实系统还应固定随机种子、使用标准数据集（如 SIFT/GloVe 或自有标注集）并报告完整的召回—延迟曲线。

玩具 IVF：本例 nprobe=1 时已找到全部精确前五项；继续增加扫描量不会提高这一查询的召回。

MECHANISM / ACCEPTANCE

验收、选型与失败边界

选向量索引不应该从“哪个库最流行”开始，而应该从自己的约束开始：数据量、维度、延迟预算、要求的召回、是否需要在库里做强权限过滤、是否接受内存换速度。把这些写成验收项，才能比较不同索引：

验收维度具体测什么常见陷阱
召回相对精确暴力结果，在标注查询集上的 Recall@k只用几个成功案例就下结论
延迟p50/p95、含过滤与序列化的端到端时间只报索引内部耗时，忽略网络与重排
过滤带租户/版本条件时的召回后过滤在低选择性查询上召回崩塌
更新插入/删除/重建后的一致性以为删除会立即回收空间
内存向量 + 图 + 元数据的真实占用只算原始向量大小
最小验收集。选 30–200 条代表性的真实查询，对每条准备好精确结果作为基线，在同一模型版本、同一向量与距离函数下，分别记录不同参数（如 HNSW 的 efSearch、IVF 的 nprobe）的召回率与 p95 延迟，画成曲线再定阈值。样本量只是启动建议，不是统计保证。

最后提醒三个容易混淆的边界：ANN 的召回率是相对“精确向量近邻”而言的，不等于“找到了能回答问题的证据”；向量检索的快，不改变上游分块与嵌入错误导致的漏检；不同嵌入模型产生的向量不可混放在同一索引中比较，升级模型必须全量重嵌。

下一篇转向另一条基线：当查询里包含型号、编号、专有名词这类需要精确字词匹配的信息时，稠密向量反而容易失灵——这正是稀疏检索与 BM25 的战场。
