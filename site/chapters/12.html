QUERY / REWRITING

查询优化与重写：
先修查询，再检索

前面所有章节都在改进检索器，却默认用户会写出一个好查询。真实用户写的是“它支持吗”“那个怎么弄”。这一篇讲清在检索之前如何改写查询：补内容、改结构，以及这些改写各自的代价与风险。

真实查询的毛病两类改写目标HyDE失败边界

MECHANISM / PROBLEM

真实查询为什么难检索？

前几章一直假设用户会写出一个清楚的查询，但真实用户的输入往往很粗糙。问题不在检索引擎，而在查询本身就没有携带足够的信息。

问题类型原始查询示例为什么检不到
查询过短“价格”信息量不足，无法区分文档
口语化“那个蓝色的图标怎么弄”噪声词多，关键词稀疏
多意图混杂“公司收入怎么样和员工人数”包含两个独立子问题，顾此失彼
指代不清“它支持吗？”代词需要上文才能解析
拼写／口语错字“机器学学”分词后与词表对不上

这些问题有共同的根源：查询表达与文档表达之间存在鸿沟。知识库里写的是“上呼吸道感染的治疗方案”，用户写的是“感冒该怎么办”；知识库里是“定价与采购流程”，用户只写了“价格”。稠密检索能桥接一部分语义鸿沟，但短查询的向量本身就没有携带多少信息，指代类查询甚至无法独立成义。

改写发生在检索前。它不改变知识库，也不改变检索引擎，而是把用户的原始输入换成对检索更友好的一个或多个查询。代价是额外的一次模型调用或规则处理，以及“改写错了会把检索带偏”的新风险。

MECHANISM / FRAMEWORK

两类改写目标

查询改写的方法看起来很多，但按目标只分两类：补全内容——让查询携带更多可匹配的语义（同义扩展、HyDE、指代消解）；改变结构——让查询适配不同的检索方式（分解成子问题、回溯成抽象问题、路由到不同通路）。分类清楚，就不会把“加词”和“拆句”混为一谈。

两类目标可以叠加：例如先把指代消解成独立问题（补内容），再把它拆成两个子问题分别检索（改结构）。但每多一步就多一次模型调用与一份出错的可能，所以真正要权衡的是改写带来的收益是否抵得上额外延迟与错误传播。

MECHANISM / HYDE

HyDE：用假答案检索

短查询的向量信息量太少。HyDE（Hypothetical Document Embeddings，假设性文档嵌入）换了个方向：先让语言模型根据查询写一段“像答案”的文本，再把这段假设文本编码成向量去检索。它的假设是——答案的措辞与真实答案文档的向量，比“问题的措辞”更接近。

流程是：用户查询 Q → LLM 生成假设文档 H → 编码器把 H 编成向量 vH → 用 vH 在知识库里检索。关键在于 H 不必正确，只要“像”知识库里的答案文本，就能把检索拉向真正答案所在的区域。

HyDE 不是万能的。假设文档可能包含错误，这些错误会把检索带偏；它也需一次 LLM 调用（延迟从百毫秒到数秒）。当知识库是结构化的规格表或法条、当查询本身已经很精确（如“劳动法第 47 条”）、或当系统对延迟敏感时，增加 HyDE 反而可能变差。上线前应在自己的标注集上对比“用 / 不用 HyDE”的实际效果。

MECHANISM / STRUCTURE

分解、回溯与路由

后三种改写不往查询里加词，而是改变它的结构。

查询分解（query decomposition）把含多个意图的问题拆成几个单一子问题，分别检索后再合并结果。“公司收入怎么样和员工人数”会被拆成“公司收入”与“员工人数”两个可以独立检索的子问题，避免一个查询同时抄两个方向而顾此失彼。子问题数量越多，检索与合并的开销也越大。

Step-Back 回溯（step-back prompting）把具体问题“退一步”成更抽象的概念问题，先去检索背景知识。“BERT 的 [CLS] 维度是多少”会先回溯成“BERT 的架构是怎样的”。这条路线适合需要先建立背景再回答的深层问题；但它同样依赖模型判断什么算“合适的抽象层级”，退得过头会检到无关的泛泛内容。

查询路由（query routing）不改变查询文字，而是决定它走哪条检索通路：事实型问题走结构化查询，概念型问题走向量检索，代码问题走代码库的 BM25，寒睓直接不检索。路由器可以用关键词规则实现（简单但覆盖不全），也可以用一个小分类器（需要标注数据）。

方法改变什么额外开销主要风险
同义扩展补词词典/规则，最低引入不相关词，抖动排序
HyDE用假设文档代替查询1 次 LLM 调用幻觉污染检索
查询分解拆成多个子问题1 次 LLM + 多次检索子问题划分错误
Step-Back抽象层级上移1 次 LLM 调用抽象过头，检到无关内容
查询路由选择检索通路0～1 次分类误路由导致漏检

MECHANISM / EXPERIMENT

无依赖的查询扩展演示

HyDE、分解、回溯都需要调用语言模型，无法在没有密钥与网络的环境里重现。这里退到一个最小可重现的例子：用一张手工同义词表做查询扩展，展示“未改写会漏检、改写后命中”这个最基本的现象。它不是 HyDE，也不是任何 LLM 改写，只是同类思路中最轻的一种。

QUERY = "价格"

# 手工同义词表：模拟查询扩展（真实系统用词典或 LLM 生成扩展词）
SYNONYMS = {"价格": ["价格", "定价", "售价", "费用"]}

docs = [
    "X-200 电机的定价说明与采购流程",   # 只说“定价”，没有“价格”
    "X-200 电机的安装步骤图解",
]

def hits(doc, terms):
    return [t for t in terms if t in doc]

for d in docs:
    print("原始:", hits(d, [QUERY]), " 扩展后:", hits(d, SYNONYMS[QUERY]))
# 预期：
# 原始: []  扩展后: ['定价']      ← 扩展把原本漏掉的文档拉了回来
# 原始: []  扩展后: []

运行条件：Python 3.10+，无第三方依赖、无网络。它验证的只是一个必要性质：查询与文档用词不一致时，扩展可以补上缺失的词项。真实的同义扩展不会手写词典，而是靠模型或检索日志挖掘，也就同时带来了引入噪声词的风险——扩展得越多，越多的文档会被“误中”。

短查询与文档用词不一致时会漏检；扩展同义词可以把漏掉的文档拉回来。

MECHANISM / FAILURES

失败边界与评估

查询改写不是“只赚不赔”：它把风险从“查询太差”换成了“改写可能改错”。下面几类失败在工程中常见。

失败模式表现应对方向
扩展过度噪声词变多，真正相关的文档被挤出前排限制扩展词数量与来源
改写跑偏模型误解意图，检到别的主题保留原查询作并行召回的一路
指代依赖上文没有历史时“它”无法消解传入会话摘要，或回退到追问
延迟与成本每个查询多一次或多次 LLM 调用缓存、小模型、仅对短/模糊查询启用

最实用的防御是多路并行：把改写后的查询与原查询一起送去检索，用上一章的融合方法合并候选。这样即使改写跑偏，原查询仍然是一条安全网。指代消解还要额外依赖会话状态：把每轮对话压缩成摘要并随查询一起传入，比把原始历史直接拼接更稳（历史越长，拼接越噪）。

评估必须“用 / 不用”对照。要证明改写有效，应在同一标注集上固定检索器、嵌入模型、索引与候选深度，只切换“是否改写”，比较 Recall@k / nDCG 与延迟。公开论文里的提升幅度绑定于特定模型与数据集，不能直接当作你系统上的预期值；本页不引用任何“提升百分之几”的数字。

至此，查询进入检索前的准备已完成。查询修好了、候选召回了、也精排过了，下一个问题是：把哪些上下文、以什么顺序与格式交给生成模型？这正是下一章——上下文增强与提示工程——要处理的内容。
