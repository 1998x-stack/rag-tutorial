AGENT / ORCHESTRATION

Agentic RAG：
让系统自己决定下一步查什么

同一个问题，信息工作者不会“一条路走到黑”：先查一点，发现不够，换个角度再查，把来源拼起来。Agentic RAG 就是把这种“规划—执行—反思”的能力交给系统。但能力越大，延迟与不确定性也越大——这一篇先把机制讲清，再谈什么时候不该用它。

MECHANISM / PROBLEM

从被动检索到主动编排

前面许多章构建的 RAG 都遵循同一条固定流水线：用户提问 → 检索文档 → 生成回答。它高效、可预测，但也被动：收到一个问题，就执行一次固定的检索与生成，不会根据中间结果改变策略。一个常见的误解是“只要检索足够好，一条流水线就能回答所有问题”。

看一个需要多步的例子：“根据过去几年类似案例的判决趋势，这个合同纠纷应该采取什么策略？”要回答它，系统得先把问题拆成“判决趋势是什么”和“类似案例有哪些”两个子问题，分别检索，再把结果拼起来做推理；如果用户追问“为什么是这个策略”，还得再去查支撑它的法条。单次检索无法把这几步串成一条链。

Agentic RAG 的改变不在“检索更好”，而在“控制流可变”。传统流水线的控制流是写死的；Agentic RAG 让系统根据中间结果选择下一步——多查一次、换个工具、还是直接生成。检索模型本身可以不变。

把这种“信息工作代理”的能力拆开，大体有四项：

  • 任务规划（Planning）：把复杂查询分解成多个子任务，并决定它们的顺序。
  • 工具使用（Tool Use）：在不同子任务上调用不同工具——向量检索、图查询、网页搜索、计算器等（前两章讲的两种检索，正好是两个可被调用的工具）。
  • 自我反思（Reflection）：评估中间结果，判断是否需要补充信息或换策略。
  • 记忆（Memory）：记住之前的检索结果与推理过程，在多轮交互中保持一致。

其中最核心的是“反思 + 再行动”的循环：先行动，看结果，再决定下一步。下面两节分别看它的朴素形式（ReAct）和工程化的形式（状态图）。

MECHANISM / REACT

ReAct：思考-行动-观察

ReAct（Reason + Act，Yao 等，2022）是 Agentic 系统里最常见的设计模式。它让模型在“思考”和“行动”之间交替：先写一段推理（Thought），据此决定调用哪个工具（Action），拿到工具返回（Observation），再进入下一轮思考。循环持续到模型认为信息够了，才输出最终答案。

它同时区别于两种极端：只推理不行动的思维链（Chain-of-Thought）拿不到外部信息；只行动不推理的流水线不会根据需要改变下一步。ReAct 把两者交织起来。

下面用一个完全确定性的玩具循环把“思考-行动-观察”走一遍。它不调用任何模型，只用关键词规则选工具，目的是把控制流看清楚：

# 玩具 ReAct 循环：用规则模拟“选工具—得到观察—再决定”
TOOLS = {
    "vector": lambda q: ["文档：退货政策 7 天内可退"],
    "calc":   lambda q: ["计算：7 - 3 = 4"],
}
QUERIES = ["退货几天", "7 减 3 等于几"]
MAX_STEPS = 2

def choose(q):
    return "calc" if any(c.isdigit() for c in q) else "vector"

for q in QUERIES:
    trace = []
    for step in range(1, MAX_STEPS + 1):
        tool = choose(q)
        obs = TOOLS[tool](q)
        trace.append(f"  第{step}步 行动={tool} 观察={obs[0]}")
        if obs:
            break
    print(f"问：{q}")
    print("\n".join(trace))
    print(f"  结束：信息够了 → 生成答案（用了 {step} 步）")
# 预期输出：
# 问：退货几天
#   第1步 行动=vector 观察=文档：退货政策 7 天内可退
#   结束：信息够了 → 生成答案（用了 1 步）
# 问：7 减 3 等于几
#   第1步 行动=calc 观察=计算：7 - 3 = 4
#   结束：信息够了 → 生成答案（用了 1 步）

运行条件：Python 3.10+，无第三方依赖、无网络。choose 是写死的规则，不是模型决策；它只能说明“控制流可以循环”，不能证明任何 Agent 的推理能力。真实系统里“选哪个工具、要不要再查”都由模型输出决定。

用规则选工具、得到观察、再决定是否结束。

MECHANISM / STATE GRAPH

计划-执行-评估循环

ReAct 是一个提示模式：模型自己写出思考与行动。工程上更可控的做法是把控制流写成一张状态图：节点是步骤函数，边（含条件边）决定下一步去哪个节点，状态在各节点间传递。LangGraph 就是这类框架的一个代表（具体 API 以其官方文档为准）。

以“计划-执行-评估”为例，一张最小状态图通常包含四个节点：

  1. 分析问题：把原始问题分解成若干子问题（这一步用 LLM）。
  2. 检索：对每个子问题选择工具并执行（向量 / 图 / 搜索 / 计算）。
  3. 评估：判断取回的信息是否足够；不足则生成一个更细的查询，回到检索。
  4. 生成答案：汇总上下文，产出带引用的回答。

“自我反思”也有对应的研究：Self-RAG（Asai 等，2023）让模型自己决定何时检索、并给生成结果加反思标记；Reflexion（Shinn 等，2023）用语言化的自我反馈改进后续尝试。它们与状态图不矛盾：反思可以就是评估节点里的一次判断。

循环必须有上限。无论是 ReAct 还是状态图，都必须限定最大步数与总 token 预算。没有上限的循环可能反复调用同一个工具而毫无进展，既拖高延迟，也无法终止。

MECHANISM / COMPARISON

传统 RAG 与 Agentic RAG

把两者的差别逐项列出，比一句“更强”有价值得多：能力换来的代价是可量化的延迟与费用。

维度传统 RAGAgentic RAG
流程控制线性、固定动态、条件分支
检索次数一次多次（依问题而定，需设上限）
工具单一向量检索多工具组合（向量 / 图 / 搜索 / 计算）
推理隐式（在生成中）显式（思考链 + 反思）
任务分解无自动分解复杂查询
错误恢复弱（一次失败即结束）可自我修正与重试
延迟 / 成本低高（多次模型调用与工具调用）
可预测性高低（执行路径随问题变化）
适用场景简单事实型问答复杂分析、多步推理
不要引用未经测量的具体倍数。原站页面里“延迟 1–3 秒 vs 5–30 秒”“Token 消耗 2–10 倍”“80% 以上查询是简单问答”“P99 < 3 秒”等数字均无可靠出处，本页已删除。延迟与成本必须在自己的模型、工具与查询分布上实测；“多少比例是简单查询”也只能从自己的日志里统计。

MECHANISM / DECISION

何时用、何时别用

Agentic RAG 不是银弹。它把能力换成延迟、成本与不确定性，所以决策的关键是把“查询分布”摸清楚，而不是一概升级。

常见适合的场景

  • 需要多步推理的复杂查询（如“综合分析某个趋势并给建议”）。
  • 要从多个异构来源综合信息（文档 + 数据库 + 网页）。
  • 需要与外部工具交互（查实时数据、做计算）。
  • 问题本身需要反复迭代与细化（如设计一个方案）。

常见不适合的场景

  • 绝大多数查询是简单的单文档问答。
  • 对延迟或成本极度敏感的在线系统。
  • 需要高确定性的场景（随机执行路径难复现）。
  • 图谱 / 工具尚未就绪，先上编排只会放大噪声。

更稳的起点是一个前置于查询分类的混合架构：简单问题走传统 RAG（快、便宜、可预测），复杂问题才路由到 Agentic 通道。分类器本身也会误分，所以它与两种通道都要分开评估（见第十八章）。

把它会怎么失效列出来，比背“它能做什么”更有用：

现象可能的根因
反复调同一个工具停不下来缺少步数 / 预算上限，或没有终止条件
子问题拆错方向规划步骤的提示或模型不足
工具选错工具描述模糊；如上一章“相似 ≠ 相关”
结果不可复现执行路径与温度引入随机性
端到端延迟不可接受简单查询也走了长循环，没有前置路由

MECHANISM / TOOLS

工具设计模式

在 Agentic RAG 里，工具是 agent 与检索世界之间的接口，它的设计质量直接影响执行效果。几条经过工程验证的模式：

  • 签名与描述清晰：工具的入参、返回与适用范围要让模型一眼看懂。描述模糊，模型就会选错工具。
  • 幂等：工具应可重复调用而不产生副作用。agent 因超时重试时，不应造成数据重复或状态混乱。
  • 错误消息结构化：失败时返回足够的信息，让 agent 能决定重试、换工具还是跳过；一句裸报错会打断推理链。
  • 带超时的执行：每个工具调用必须设置超时；一个卡住的调用不应阻塞整个循环。
工具的数量本身也是成本。工具越多，模型选错的概率越高，描述与评估的维护量也越大。先从少量高价值工具开始，缺什么再加，而不是一开始就把所有系统都接进来。
