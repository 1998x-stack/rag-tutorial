MULTIMODAL / RETRIEVAL

多模态 RAG：
当知识库里不只有文字

产品手册里的爆炸图、财报里的趋势图、流程图、会议白板照片——这些信息纯文本检索接不住。多模态 RAG 的起点不是“把图交给多模态大模型”，而是先用一个共享嵌入空间，让图像和文本能放进同一套检索里。这一篇从 CLIP 的双编码器讲起，再谈表格、生成与新的失败边界。

MECHANISM / PROBLEM

文字之外的检索

前十八章默认了一件事：知识库由纯文本构成。但真实的文档里，很多信息并不落在文字上——产品手册用爆炸图标出零件位置，财报用折线图表达趋势，流程用方框和箭头表达先后，维修记录里还有现场照片。把这些内容都“转成一段描述文字”再索引，往往是最省事也最容易丢信息的一步：图里“哪个零件挨着哪个”的空间关系，很难用一句摘要保真地表达出来。

于是出现两个常见的误解。第一个是“多模态 = 换一个能看图的生成模型”：只要最后的 LLM 能读图，问题就解决了。但检索这一半没有变——如果按文本查询根本找不到那张相关的图，再强的生成模型也无图可用。第二个是“图像检索就是把图也做一次 embedding”：真正难的不是给图算一个向量，而是让图像的向量和文本的向量落在同一个空间里，使“一句话”能直接和“一张图”比距离。这正是 CLIP 这类模型要解决的问题，也是本章的起点。

先把“检索”和“生成”分开看。多模态 RAG 有两个彼此独立的环节：多模态检索（把图/文放进一个可比的空间）与多模态生成（让模型读懂召回的图再作答）。它们可以单独升级，失败原因也常常不同。本章按这个顺序展开。

为了说清机制，下面用一个具体的检索需求当例子：用户输入一句文本描述，系统要在图库里找出最匹配的图片。我们要回答的是——模型凭什么知道“这段文字”和“那张图”相似？

MECHANISM / MODEL

CLIP 与共享嵌入空间

CLIP（Radford 等，2021）解决的核心问题是：如何让“一段文字”和“一张图”变得可比。它的做法是训练两个编码器——一个把图像变成向量，一个把文本变成向量——并让它们的输出落在同一个嵌入空间里。这里的关键不是“把图也变成向量”，而是两个编码器输出的向量维度相同、且可相互比较。

训练时，一批图文对同时进入两个编码器，得到一批图像向量和一批文本向量。训练目标让真正配对的图文在空间里彼此靠近，而把不配对的组合推远（对比学习）。据论文摘要，CLIP 在约 4 亿对图文上训练；配对的整理与负样本的构造方式依训练流程而定，具体细节以原论文为准。

检索时，两边的向量都不必重新走一遍生成模型，只要算一个简单相似度。“像不像”被度量成了一个数：

sim(v,t)=v⋅t‖v‖‖t‖

其中 v 是图像向量，t 是文本向量，两者维度相同（记为 d）。分母是 L2 范数，所以结果只反映方向相似度，不受向量长度影响——这一点和第六章讲过的双编码器检索完全一致。把文本向量与库里每一张图的向量都算一遍，再排序，就得到图像检索结果。

MECHANISM / RETRIEVAL

图文互检的对称性

因为图像和文本落在同一个空间里，相似度就可以双向使用：用一句文本找图（文本→图），或用一张图找最接近的文本（图→文）。同一个空间还能当“零样本分类器”用：把候选类别名当作一段段文本编码，哪段文本向量离这张图最近，就归到哪一类——无需为每个新类别重新训练分类头。

“双编码器”指的是结构对称，不是共享权重。CLIP 的图像编码器与文本编码器通常是不同结构的两个网络（图像侧常用 ViT / ResNet，文本侧是 Transformer），它们被训练到共享的空间，但参数并不共享。不要把“落在同一空间”误读成“用同一个 encoder”或“必须共享权重”。这一点在第九章讲 DPR 双编码器时同样适用。

下面这个小实验把“文本向量比图库”变成能跑的东西。它只用标准库和人为指定的二维向量，目的是把余弦相似度的算术走一遍：

# 用二维人工向量演示“图文互检”：只是余弦相似度的算术
import math

def cos(a, b):
    return (a[0] * b[0] + a[1] * b[1]) / (math.hypot(*a) * math.hypot(*b))

query_text = [0.95, 0.30]   # text encoder output (hand-picked)
images = {                   # image encoder outputs (hand-picked)
    "图A 装配示意": [0.90, 0.20],
    "图B 折线趋势": [0.10, 0.98],
    "图C 无关照片": [-0.80, 0.30],
}
ranked = sorted(images.items(), key=lambda kv: cos(query_text, kv[1]),
                reverse=True)
for name, vec in ranked:
    print(f"{name}\t{cos(query_text, vec):.3f}")
# 预期输出：
# 图A 装配示意	0.996
# 图B 折线趋势	0.396
# 图C 无关照片	-0.787

运行条件：Python 3.10+，无第三方依赖、无网络。它只能证明“在这组手写向量下，余弦相似度算出了这个排序”，不是任何真实模型（如 CLIP）的输出。真实检索结果的排序完全取决于编码器训练得好不好、以及图库里到底有没有相关的图。

MECHANISM / ENGINEERING

表格：没有唯一答案

表格是半结构化的：它既可以被当成文字，也可以被当成图像。第四章讲过“PDF 抽取文字不等于恢复阅读顺序”，表格正是最容易丢结构的地方——合并单元格、单位、表头与数据行的对应关系，一旦压成一行文本就很难恢复。所以表格的检索路线不止一条，选哪条取决于你更需要“找到表”还是“从表里算出一个数”。

路线做法适合代价 / 局限
转文本把表格转成 Markdown / CSV 后按文本索引简单键值表、只求找回原表丢失行列与单位语义；复杂表结构会乱
自然语言摘要让 LLM 写一段“这张表里有什么”再索引表很多、只需要模糊定位摘要会丢细节；表一变就要重新生成
向量 + SQL 混合表名/描述走向量检索，数据用 SQL 精确查需要精确计算、聚合的报表工程量大；需要表结构接入数据库
视觉文档检索把整页当图像，用多模态嵌入直接检索版面复杂、不想丢失视觉结构不知道列的含义，难以精确聚合数字

这四条路线不是四选一：常见做法是先按文本/摘要找回候选表，再决定要不要用结构化查询或视觉模型去读细节。选型的关键不是“哪种最好”，而是先回答“用户到底要表里的哪一部分信息”。

能找回 ≠ 能算对。多模态嵌入擅长“这张表和我的问题相关吗”，但它不理解列的含义；涉及求和、比较、单位换算的查询，仍然需要表格的结构化解析或数据库查询。把“检索相关性”和“数值正确性”分开评估。

MECHANISM / GENERATION

用 VLM 基于图像生成

检索找回相关图像与段落之后，下一步是让模型看懂图并基于图作答。这需要一个视觉语言模型（VLM）：它同时接受图像和文本，输出文本回答。开源侧有 LLaVA（Liu 等，2023）、BLIP-2 等，商业侧有各家的多模态模型；具体版本与能力以各自官方文档为准。

把流程展开，它比纯文本 RAG 多了一步“组装”：

  1. 输入：用户的问题可能同时包含文字与一张图（比如“这张照片里的设备怎么保养”）。
  2. 检索：文本与图像都先变成向量，在图文混合索引里取回最相关的段落与图片。
  3. 组装：把取回的文本段落和图像（或其路径）拼成一段多模态上下文，交给 VLM。
  4. 生成：VLM 结合图文上下文输出回答，并标注每条信息的来源。
“对齐”是新的难点。一张产品照片显示“红色外观”，而说明书文字写“有红色和蓝色两种版本”——系统要理解这两者并不矛盾，而是互补。图与文之间的关系（补充、例证、还是冲突）不会自动被模型正确识别，高风险的场景仍然需要人工核对。

注意：这里的“检索”与“生成”用的是不同模型。检索用 CLIP 一类的双编码器，生成用 VLM；两者的评估口径不同。混用它们的分数去下结论，就像用检索指标去评价生成质量一样，是错位的。

MECHANISM / FAILURES

工程成本与失败边界

多模态 RAG 在存储、延迟、评估上都比纯文本复杂。先把几条常见的工程结论列出来，再说哪些是真失败、哪些只是成本：

  • 存储：除了文本向量，还要存图像向量和图像文件本身；图像向量维度通常不低，图库一大会明显抬高存储。具体倍数依模型与压缩方式而定，不要拿“十倍/百倍”当恒定值。
  • 延迟：VLM 的推理通常比纯文本 LLM 慢。实用做法是对“多模态查询”和“纯文本查询”做路由：不需要看图的问题不要走 VLM，以免平白抬高延迟。
  • 细粒度识别：CLIP 类模型文档中自己就提到对细粒度区分、计数和空间关系较弱。区分两个相近型号、数图中有几个零件，不要只依赖多模态嵌入。
  • 评估：第十八章的忠实度指标要扩展到图像：生成描述与原始图像是否一致。图像层面的核对比文本对比更难，不能直接沿用文本口径。

把失败情形和它们真正的根因对照起来，才能避免“看到效果差就换模型”的反射动作：

现象可能的根因先查什么
明明库里有图却搜不到文本与图像没落到可比的空间，或图未被编码入库先看该图向量是否存在、文本查询与它的相似度排名
搜到了图但回答错VLM 没看懂图，或图文关系冲突未被识别固定召回结果，单独测 VLM 能不能答对
相近型号总混淆多模态嵌入对细粒度特征不敏感加专用分类模型或 OCR / 元数据过滤前置
延迟高得不可用所有查询都走了 VLM，没有路由统计多模态查询占比与各自延迟分位
不要相信任何未实测的多模态收益数字。原站页面里“企业文档 60% 知识非文本”“企业项目 70% 涉及非文本模态”“图像存储是文本的 10–50 倍”等表述没有可核对的出处，本页已删除。这类数字必须换成你自己知识库的实测统计，并在同一批查询、同一版本索引与模型下比较。

从文本 RAG 到多模态 RAG 是一次架构升级，而不是一个插件开关。它把“把什么变成向量”和“拿回来之后怎么读”这两个问题都放大了。
