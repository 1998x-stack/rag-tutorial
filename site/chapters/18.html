EVALUATION / METRICS

RAG 评估体系：
怎样知道系统到底好不好

检索召回率涨了，用户却说“不准”——这说明只盯一个指标会制造假象。评估要同时看“找对了没”“答得好不好”“跑得快不快”，而且要能在同一套标注上比较。这一篇拆开这四个问题，并说清每个指标到底依赖什么。

三维框架检索指标RAGAS基准与反馈

MECHANISM / PROBLEM

“到底有多好”是个端到端问题

先摆一个常见的误解：把检索的召回率当成“系统质量”。一个例子就能说明为什么不行——检索把正确文档找回来了，但生成阶段把召回的一堆低相关文档全部摍进上下文，最终回答反而变差。此时召回率是涨的，用户体验却是降的。

除了单指标陷阱，“好”还同时包含三个彼此不同的子问题：找对了吗（检索）、答得好吗（生成）、跑得动吗（系统）。它们不总是同向变化，所以要分别度量、再综合判断。评估的最终目的不是得到一个分数，而是能回答：“改动了 X，系统是变好还是变坏？”

评估必须有基准集与可比性。没有标注过的基准集，就没有客观的“好”。而且比较时必须在同一套问题、同一份答案、同一版本索引与模型下进行；拿不同口径的数字相比，得到的“提升”是假的。这一点会贯穿本章。

MECHANISM / DIMENSIONS

三维评估框架

把评估拆成三个维度，每个维度有各自的常用指标：

先固定口径，再谈“提升”。k 取多少、相关性如何标注、忠实度用什么判定，都必须先写进评估方案。否则每次跑出来的数字都不可比，“提升”也就无从谈起。

MECHANISM / METRICS

检索指标：Hit / MRR / NDCG

检索指标都需要一份相关性标注：对每个查询，哪些文档算相关。有了它，就能用几个互补的角度衡量排序质量：

指标回答的问题口径
Hit Rate@k前 k 条里到底有没有相关的？只要前 k 条含至少一条相关文档就计 1，再对查询取均值
Recall@k所有相关文档里，前 k 条覆盖了多少？前 k 条中相关数 / 全部相关数
MRR第一个相关文档排得多靠前？第一个相关文档名次的倒数，再对查询取均值
NDCG@k整体排序质量（位置加权）按位置对相关度打折，再与理想排序归一化

MRR 把“第一个相关文档的位置”变成一个可平均的数：

MRR=1|Q|∑q=1|Q|1rankq

其中 |Q| 是查询总数，rank_q 是第 q 个查询的第一个相关文档的排名（从 1 开始）。若某个查询一条都没检到，它的贡献记为 0。

Hit Rate 与 Recall 不同，容易混淆。Hit Rate 只问“至少命中一个没”，对“全部相关是否到齐”不敏感；Recall@k 才看覆盖率。一个查询可能有 5 篇相关文档，前 k 条里只到 1 篇——Hit Rate 给满分，Recall 只给 0.2。因此两个都应看。BEIR 等基准提供了跨数据集比较检索指标的标准做法。

MECHANISM / RAGAS

RAGAS 四指标与依赖

RAGAS（Es 等，2023）是一套把生成与检索质量自动化的指标集。它的四个核心指标看起来相近，但依赖的输入不一样，弄混就会用错：

指标衡量大致原理需要参考答案？
Faithfulness回答是否忠于检索上下文把回答拆成声明，逐条用上下文核验否
Answer Relevancy回答是否切题用回答反向生成问题，与原问题比语义相似度否
Context Precision相关上下文排得靠不靠前按位置对相关上下文加权是
Context Recall需要的信息是否都检索到了从参考答案反推所需上下文并比对是
自动指标不是人工判断的替代品。Faithfulness 与 Answer Relevancy 常用一个 LLM 来判定，因此会受所用模型影响（上一章的 NLI 也有假阳/假阴）。RAGAS 让评估得以规模化，但它给出的是“近似信号”，高风险场景仍需抽样人工核对。

MECHANISM / PIPELINE

离线基准与在线反馈

评估分两半：离线用固定的基准集反复跑，保证可比；在线收集真实用户的反馈，发现基准集没覆盖到的问题。

黄金数据集是离线评估的基石。一个好的基准集不只是“能回答的问题”，而应三类都要有：

  • 典型查询：覆盖知识库中最常见的提问方式，取自真实用户日志并人工标注答案与相关上下文。
  • 边界查询：模糊查询（“给我讲点有用的”）、多义查询（“苹果”是水果还是公司？）、跨领域查询，用来测鲁棒性。
  • 对抗查询：知识库中根本没有答案的问题（测拒答）、含误导信息的查询、以及提示注入尝试。

基准集不是一次性资产：它需要随着知识库与用户行为的变化定期补充与清理，否则会逐渐“过时”。

在线反馈补上离线看不到的部分：

信号来源含义（需谨慎解读）
显式反馈“有用/无用”按钮 + 补充说明质量高但参与率低，样本有偏
隐式反馈复制文本、追问、立即离开只是行为相关，不等于“对/错”
反馈回环把“无用”样本存入待改进队列定期分析共同模式，定位要改的环节

把离线评估接进 CI/CD，能让每次改动都被“秤”一下：变更触发 → 在隔离环境跑基准集 → 与基线对比 → 指标下降超过预设阈值就阻止合并，并给出回归到具体样本的报告。注意阈值是工程约定，不是书本定值。

用 LLM 当评审（LLM-as-a-judge）方便，但有偏差。用另一个模型给答案打分可以规模化，但评分会受提示、模型版本与位置偏差影响，不同模型打分不可直接互比。把自动评分当作可重现的辅助信号，高风险场景仍需人工抽查。

MECHANISM / EXPERIMENT

纯 Python 演示：MRR 与 Hit@k

下面用一个手写的“第一个相关文档名次”列表把这两个指标算出来。它把公式变成了能跑的东西，也能看出两个指标关注点不同：

# 计算 MRR 与 Hit@3：只用标准库
# 每个查询中“第一个相关文档”的名次；None 表示一条都没检到
first_relevant = [1, 3, None]

mrr = sum(1 / r for r in first_relevant if r) / len(first_relevant)
hit3 = sum(1 for r in first_relevant if r and r <= 3) / len(first_relevant)

print("MRR   =", round(mrr, 4))
print("Hit@3 =", round(hit3, 3))
# 预期输出：
# MRR   = 0.4444
# Hit@3 = 0.667

运行条件：Python 3.10+，无第三方依赖、无网络。它只能证明“在这三个已经标好的名次下，公式算出了这两个数”，不能证明任何检索系统好坏——真实指标完全取决于你标了哪些相关文档。如果某个查询根本没检到，它的贡献记为 0。

根据第一个相关文档的名次，分别算出 MRR 与 Hit@3。

MECHANISM / FAILURES

失败边界与解读陷阱

评估本身也会出错。下面这些是常见的“数字看起来没问题，结论却错”的情形：

陷阱表现后果
口径不一致不同报告里 k 或相关性标注不同数字不可比，得到假的“提升”
混用模型/版本拿不同嵌入、不同索引版本或不同判官模型的分数相比排名与结论不成立
只看单一指标只盯召回率或只看延迟局部优化损害整体
基准集过时问题不能代表当下用户需求离线变好、线上变差
LLM 评审偏差评分受判官模型、提示与位置影响分数不可重现、不同模型不可比
在线反馈有偏反馈者不是随机样本不能代表全体用户体验

指标指向的改进方向也值得记住，避免“看到分数低就乱改”：

  • 忠实度低：先看生成提示是否强制依据资料，再考虑模型遵循能力。
  • 上下文精确率低：重排序可能需优化，或嵌入质量不足导致相关文档排名靠后。
  • 上下文召回率低：分块可能太粗导致信息丢失，或 top-k 太小。
  • 答案相关性低：查询改写可能有问题，或上下文冲突污染了回答。
  • 延迟高：换更轻的嵌入模型、减少 top-k、或引入缓存。
没有评估的系统等于盲飞。但有了评估也不等于有了正确答案——指标是帮你发现问题的工具，而不是问题的答案。每一次改动都要在同一套基准、同一版本下对照，才能把“看起来变好”和“真的变好”区分开。评估方法的具体实现与参数，以 RAGAS、BEIR 等基准的官方文档为准。

掌握了如何衡量系统，下一步是把能力拓展开：当知识库里包含图像、表格、图表甚至音频时，检索与评估都要换一套思路——这是下一章多模态 RAG 的主题。
