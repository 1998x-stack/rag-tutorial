RETRIEVAL / HYBRID

混合检索：
融合稀疏与稠密

上一章的稀疏检索与再上一章的稠密检索各有一半的查询会失手。这一篇解释如何让两路并行召回、再用一个不依赖分数刻度的融合算法把候选合成一个排序，以及它为什么有效、又在哪里出错。

MECHANISM / PROBLEM

单一检索为什么不够？

稀疏检索（BM25）只在查询词与文档词重合时起作用；稠密检索只在编码器把两者映射到相近向量时才起作用。没有哪一种能覆盖全部查询。下面这张表把两类查询并排放在一起——只要换一个查询类型，同一套检索系统就会从“很好用”变成“完全找不到”。

用户查询期望结果BM25 稀疏稠密向量
“X-200 电机额定功率”精确型号对应的手册页命中：型号是完整词项易混：X-210 语义几乎相同
“劳动法第 47 条”法条原文命中：编号精确易偏：检索到解读文章
“感冒了该怎么办”“上呼吸道感染治疗方案”失灵：没有共同词项命中：语义相近
“最近上火该吃点什么”口语化的食疗建议失灵：关键词稀疏命中：理解口语表达

型号、编号、专有名词要求字面精确，同义改写、口语化、跨语言要求语义泛化。两类需求天然拮抗：把向量调得更“泛”会牺牲精确，把词项调得更“严”会牺牲召回。这正是混合检索（hybrid retrieval）的出发点。

是互补，不是叠加。混合检索不是“稀疏分数 + 稠密分数”，两路的分数刻度完全不同，直接相加没有意义。它要做的是并行召回、再用名次（而非分数）融合。表中“命中／失灵”为教学示意，具体表现取决于分词、模型与语料，需在你的标注集上实测。

MECHANISM / STRUCTURE

两条召回通路

混合检索把同一个查询同时送给稀疏与稠密两套引擎，各自返回一个有序候选列表，再用融合算法合并成一个排序。关键是：两路是并行且相互独立的，融合发生在“拿到两个列表之后”，所以任何一路的分数刻度都不会污染另一路。

工程上，两路的候选深度不宜太小：如果每路只取前 5，那么“被 BM25 排到第 20、但被稠密排到第 3”的文档根本没机会进入融合。常见做法是每路先取 Top-50～Top-200 再融合。这个数字是工程经验区间，不是定理，需按延迟预算与语料规模调整。

MECHANISM / RANK FUSION

RRF：按名次融合

两个列表怎么合？一个自然想法是“把分数加起来”，但 BM25 的分数可以是 0～几十，余弦相似度是 −1～1，加起来等于拿尺子量温度。倒排排名融合（Reciprocal Rank Fusion，RRF）换了个思路：完全丢掉分数的数值，只看每个文档在各路里的名次。名次是跨引擎可比的——不管分数怎么算，第 1 名总比第 3 名靠前。

RRF 的另一个好处是天然处理“只出现在一路”的文档：某文档只在 BM25 里排第 3、在稠密里没出现，它仍然拿到 1/(k+3) 的分数，不会被直接丢弃；反之，两路都排前列的文档得分叠加，被顶上来。这也是 RRF 成为默认融合方法的原因。

MECHANISM / EQUATION

RRF 公式

给定文档 d 和若干路检索系统，RRF 把 d 在每一路里的名次取倒数后求和：

RRF(d)=∑i1k+ranki(d)

其中 ranki(d) 是文档 d 在第 i 路结果里的名次（从 1 开始）；若 d 未出现在该路里，则该项为 0。k 是一个正的平滑常数。两路都用 RRF 时，文档分数就是两路倒数之和——这正是上一张图里 doc_B 拿到 0.0325 的来源。

k 控制“头部名次”的权重。k 越小，前几名之间的差距越大（1/1 与 1/2 差一倍）；k 越大，名次差距被抹平（1/61 与 1/62 几乎相等），融合更接近“投票”。实践中 k=60 是被广泛沿用的默认值，它来自 RRF 的原始论文（Cormack、Clarke、Buettcher，2009）；但 60 是经验值，不是最优解的保证，换语料应重新验证。

名次口径要一致。“名次从 1 开始还是从 0 开始”会改变结果；多路融合时每一路都必须用同一种口径，并且对“未召回的文档”统一按不存在处理，而不是当成最后一名。不同实现的 RRF 得分因此不可直接比较。

MECHANISM / ENGINEERING

其它融合与多路召回

RRF 不是唯一的融合方法。它们的主要区别在于：是否相信分数的数值，以及是否需要训练数据。

融合方法依据优点代价
RRF只看名次无需分数归一化，鲁棒、免训练丢弃了分数差别的信息
加权求和归一化后的分数可调两路权重，保留分数需选归一化方式，权重难定
学习排序（LTR）人工特征 + 标注在标注集上可逼近最优需要标注数据，维护成本高
交替合并（interleaving）两路轮流取简单，保持来源多样性不考虑置信度，顺序敏感

若选加权求和，必须先解决分数不可比的问题：BM25 原始分范围大，常做 Min-Max 或 Z-Score 归一化，再按权重相加。这里没有普适权重；权重应由标注查询集上的实验决定，而不是拍脑袋。

生产系统往往不止两路。除了向量与 BM25，还可以并行接入：图检索（沿知识图谱关系做多跳，适合“某公司旗下的产品”这类实体关系查询）与结构化查询（直接查数据库，适合“上季度销售额最高的品类”这类聚合问题）。所有通路的结果用同一个融合器合并。路数越多，融合前的去重与打分口径就越重要。

MECHANISM / EXPERIMENT

纯 Python 实现

下例用标准库实现 RRF：输入是两路“按名次排好序的文档 ID 列表”，输出是融合后的排序。它要验证的不变量是：名次越靠前、且出现的路数越多，融合分越高；同时只在单路出现的文档不会被丢掉。

def rrf(results_list, k=60):
    """results_list: 每路一个已按名次排好序的文档 ID 列表"""
    scores = {}
    for results in results_list:
        for rank, doc_id in enumerate(results, start=1):  # 名次从 1 开始
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    # 按融合分降序；分数相同则按文档 ID 保证确定性
    return sorted(scores.items(), key=lambda kv: (-kv[1], kv[0]))

bm25  = ["doc_A", "doc_B", "doc_C"]   # BM25 第 1、2、3 名
dense = ["doc_B", "doc_D", "doc_A"]  # 稠密第 1、2、3 名

for doc_id, score in rrf([bm25, dense]):
    print(f"{doc_id}  {score:.4f}")
# 预期（k=60）：
# doc_B  0.0325   （名次 2+1）
# doc_A  0.0323   （名次 1+3）
# doc_D  0.0161   （仅稠密第 2）
# doc_C  0.0159   （仅 BM25 第 3）

运行条件：Python 3.10+，无第三方依赖、无网络。这里手算的分数只用于验证算法逻辑；真实系统应把两路召回的完整排序输入融合，并在标注集上比较融合前后的 Recall / nDCG。

RRF 只看名次：两路都靠前的文档得高，单路出现的文档也不会被丢。

MECHANISM / FAILURES

失败边界与工程建议

融合算法本身很少出错,出错往往在它拿到的输入或评估方式上。

失败模式表现应对方向
长文档天然占优很长的详情页被两路同时抬到前列长度惩罚、统一分块粒度
分数不可比加权融合时权重失效先归一化,或改用 RRF
名次口径不一结果难复现统一 rank 起点与未召回处理
只看单路指标以为融合一定更好在标注集上比融合前后 Recall/nDCG

最后强调两个容易被忽略的边界:混合检索提升的是"召回质量",不是"答案质量"。如果分块与嵌入本身已经把证据切碎,融合不会把它拼回来。其次,两路召回的候选必须去重(同一文档可能被两路返回,且可能是同一篇的不同分块),否则融合列表里会出现重复条目,干扰下游重排与生成。

评估要与上线一致。比较融合方案时,必须固定分词器、嵌入模型、索引版本与候选深度,只改变融合算法;否则不同步的变量会让差异无法归因。融合效果也是相对的,没有"混合一定优于单路"的保证,取决于查询分布与语料。
