GENERATION / CONTEXT

上下文增强与提示工程：
检索之后的最后一公里

候选文档已经被召回并排好序，但它们不会自动变成好答案。这一篇解释上下文为什么是一个有预算上限的容器、文档摆在哪里会影响模型是否用得上、提示怎么措辞才不给出“自作主张”的出口。

有限预算位置效应排列策略提示约束

MECHANISM / PROBLEM

检索对了，答案为什么还差？

假设检索与重排都工作正常，正确的文档已经排在前面。把它们直接拼起来交给语言模型，答案却可能仍然不准：引用错了页码、把通用知识当成文档内容、或干脆把最相关的那段忽略了。问题不在检索，而在上下文怎么被组织和表述。

把文档拼接起来“加个问题”，看似简单，实则要同时回答四个问题：能塞多少（预算）、放在哪里（位置）、怎么写指令（提示）、多余内容怎么处理（压缩）。它们互相牵制：多塞一篇文档可能把最相关的挤到中间；约束没写清楚，模型就会“自由发挥”。

上下文增强是一道取舍题。没有“把所有候选都写进去”这个选项——上下文窗口有上限，且信息越多、噪声越多。接下来的几节分别处理预算、位置、提示与压缩这四个变量。

MECHANISM / BUDGET

上下文是有限预算

语言模型的上下文窗口有上限（不同模型从数万到数十万 token 不等，且会随版本变化），但“没装满”不等于“应该装满”。把检索到的文档全部塞进去会同时付出三个代价：

  • 位置稀释：真正相关的文档被推到上下文中间，反而更难被用上（下一节展开）。
  • 信噪比下降：低相关文档会稀释高相关文档的影响力，让模型难以分辨什么重要。
  • 成本与延迟：输入 token 越多，推理越慢、越贵。

因此应该给上下文设一个预算上限，而不是“能用多少用多少”。预算的合理值取决于任务：事实问答通常只需几个高相关片段；需要归纳或对比的任务则需要更多材料。

“2000～6000 token”只是一个常见工程区间，不是定律。3～5 个高质量片段常常能覆盖大多数问答，但这个数字依赖于模型、分块大小与问题类型。请用自己语料上的评估来决定预算，并用所选模型对应的 tokenizer 计数，不要把字符数当成 token 数。

MECHANISM / POSITION

Lost in the Middle：位置会改变利用率

把一段相关文档放在上下文的什么位置，会显著影响模型是不是用得上它。Liu 等人 2023 年的研究（“Lost in the Middle”）发现：当关键信息位于上下文开头或结尾时，模型的利用率较高；一旦被放到中间，利用率会明显下降，呈现出 U 形曲线。

这条现象的直接含义很实用：把最相关的文档放在上下文的两端，而不是中间。它也解释了“为什么塞得越多不一定越好”——每多塞一篇不相关文档，就可能把真正重要的那段推向更靠中间的位置。

曲线是定性示意。U 形的具体形状与幅度随模型、任务、提示和评测方式变化，不同模型不一定都呈同一形状。原始论文给出了其在特定长上下文任务上的观察；本图只用于说明“位置重要”，不得当作你系统上的预期数值。

MECHANISM / ORDERING

文档排列策略

既然两端比中间更容易被用上，就可以主动设计文档的排列方式。

策略做法优点缺点
相关度降序最相关放最前简单，首置信息最强未利用结尾位置
相关度升序最相关放最后利用结尾位置读者/模型先看到不相关内容
“三明治”最相关放两端，次相关放中间同时利用开头与结尾中间内容可能被忽略
交替排列按来源/类型交替降低单一来源偏好可能打乱逻辑连贯性

没有普适最优的排列。经验上，“三明治”（最相关放两端）常能兼顾首尾两个高关注区，但它是否优于简单降序，取决于模型与任务，应在自己的评估集上验证。一个更稳的做法是：把相关度作为排列的主要依据，把最强的一两篇放在两端，而不是关心中间段的精确顺序。

MECHANISM / PROMPT

提示模板：把约束写清楚

提示模板是 RAG 的“最后一公里”：它决定模型是只看提供的资料，还是可以“自由发挥”。一个常见的坑是模板里写了类似“如果你知道答案，可以直接回答”——这句话看起来宽松友好，实际上给了模型一个逃避查阅资料的出口。即使知识库里的版本更新、更准确，模型也可能用自己训练时的旧知识回答。

你是知识库问答助手。只能依据下面提供的资料回答，不得使用资料之外的知识。

【资料】
[1] 【内容】
    来源：【标题 / 页码 / 日期】
[2] …

【问题】【用户问题】

【要求】
- 每个事实后用 [编号] 标注来源。
- 资料不足以回答时，明确说“根据提供的资料无法回答”。
- 不得编造资料中没有的数字、名称或来源。

好的 RAG 模板通常包含四个要素：角色（做什么）、资料边界（只能看什么）、引用要求（怎么标来源）、拒答出口（答不了怎么办）。这四条把模型的自由度限制在“忠实地从资料里找并标注”，而不是“凭记忆编”。

上面的模板是示意文本。不同模型的指令遵从度不同，同一模板换模型也可能变差。它也无法保证消除幻觉：即使写了“只能依据资料”，模型仍可能误引或摘要出错（这属于下一章生成与引用溯源的内容）。模板要改就用评估集对照，不要只凭感觉。

MECHANISM / ASSEMBLY

压缩、元数据与拼装

当片段本身很长时，直接原文塞入会浪费预算。常见的三种压缩方式是：

  • 令牌级压缩：如 LLMLingua，用小模型逐句评估与查询的相关性，丢掉低相关句子，论文报告可在保持任务表现的同时大幅压缩提示。它需额外模型与一次推理，且压缩本身可能丢细节。
  • 选择性过滤：按元数据（标题、章节）做粗粒度筛选，只保留可能相关的章节，成本低但依赖元数据质量。
  • 摘要式压缩：用 LLM 先给每个片段生成短摘要再拼入，适合超长文档，但摘要可能遗漏关键限定词。

另一种提升“可用性”的做法是元数据注入：不只传“2024 年营收增长 20%”，而是传“据【公司 2026 年报】第 5 页，2026 年营收增长 20%”。带上标题、页码、日期与检索/重排分数，模型才能判断资料的来源与时效，也为下游引用溯源提供依据。代价是元数据自身占 token。

MECHANISM / EXPERIMENT

纯 Python 演示：位置决定“曝光度”

下例用一个人为设定的 U 形权重函数把“两端高、中间低”这个现象写成一个可计算的量，展示同一条相关文档换一个位置、它的“曝光度”就不同。这个权重是我们自己定的形状，不是从模型里测出来的，它只用于说明位置为什么值得规划。

# 人为设定的 U 形位置权重：开头与结尾高、中间低
# 仅为教学示意，不代表任何模型的实测注意力
def position_weight(pos, n):
    x = pos / (n - 1)                 # 0（开头）.. 1（结尾）
    return 0.2 + 0.8 * (2 * x - 1) ** 2

n = 5
orders = {
    "相关文档放最前": ["R", "d2", "d3", "d4", "d5"],
    "相关文档放中间": ["d2", "d3", "R", "d4", "d5"],
}
for name, docs in orders.items():
    pos = docs.index("R")
    print(name, "→ 曝光度 =", round(position_weight(pos, n), 2))
# 预期（权重为手写函数，非模型输出）：
# 相关文档放最前 → 曝光度 = 1.0
# 相关文档放中间 → 曝光度 = 0.2

运行条件：Python 3.10+，无第三方依赖、无网络。它能证明的只是“在给定这个 U 形假设下，位置会改变曝光度”，不能证明真实模型也恰好是这条曲线。真实的位置效应要靠在你的模型与任务上做消融（把同一相关文档放到不同位置、比较答案正确率）才能得出。

同一条相关文档，放在两端比放在中间获得更高的曝光度。

MECHANISM / FAILURES

失败边界与评估

上下文组装看似只是拼接字符串，但每一处细节都可能成为失败点。

失败模式表现应对方向
提示留了出口模型用自己的旧知识而非资料回答去掉“可直接回答”类措辞，强制引用
上下文过满最相关文档被挤到中间设预算上限，控制片段数
位置浪费关键文档恰好在正中两端放最相关，三明治排列
压缩丢细节关键限定词、条件被删除保留关键句，按任务调压缩强度
元数据噪声页码/分数占满预算却无用只注入与判断相关的元数据
评估要拿端到端指标。上下文策略的好坏最终体现为答案正确率、引用准确率与延迟，而不是“上下文看起来更整齐”。要比较不同排列、不同预算、是否压缩，必须固定检索与模型，只改上下文策略，并在同一标注集上对照。本页不引用任何“提升百分之几”的数字。

到这里，检索与上下文都已就绪，只剩最后一步：生成。但生成本身也会引入新的风险——模型可能错引来源、把资料里的话说成自己的、或在资料不足时强行作答。如何让回答“有据可查”，是下一章生成与引用溯源的主题。
