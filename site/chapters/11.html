RETRIEVAL / RERANKING

重排序：
交叉编码器与两阶段精排

混合检索把“可能相关”的候选召回了一大堆，但它们的排序仍来自粗糙的近似分数。这一篇解释为什么让查询与文档直接交互能排得更准、这种精度为何无法预先算好，以及精排会在哪里帮倒忙。

粗排的局限两阶段架构交叉编码器失败边界

MECHANISM / PROBLEM

为什么粗排不够？

前两章的检索阶段都有一个共同点：查询与文档在编码时彼此看不见。双编码器把两者分别映射成向量再点积，BM25 把两者当成词项集合相加。它们得到的是“整体有多接近”的粗糙近似，而不是“这篇文档能不能回答这个问题”的精细判断。

看一个具体例子。用户搜索“苹果公司 2026 年财务状况”，候选里有：

候选文档与查询的整体语义相似度能不能回答问题
A：苹果公司的发展历史与公司沿革很高（都围绕“苹果公司”）不能，里面没有财务数字
B：苹果公司 2026 年营收与利润披露高能，正面回答

A 与 B 的整体语义都“很像”查询，单靠向量相似度很难把“正好含有所需方面”的 B 稳定地排在 A 前面。问题根源是：相似度衡量的是整体接近程度，而用户的查询往往只关心其中某个方面。把查询与文档放在一起、让模型逐词比对，才能看到“财务”这个具体落点有没有被覆盖——这正是重排序要做的事。

重排序不是重新检索。它不改变候选集合，只改变候选的顺序。如果正确的文档根本不在第一阶段召回的 Top-N 里，重排序无能为力。表中的“相似度高／不能回答”为教学示意，用于说明机制，不是某个模型的实测结果。

MECHANISM / ARCHITECTURE

两阶段架构

重排序把检索拆成两步：第一阶段“广撒网”用双编码器或混合检索从全量库里快速召回 Top-N 个候选，目标是不漏；第二阶段“精挑细选”用一个更重但更强的模型对这 N 个候选逐一重新打分，取 Top-K 送给生成，目标是排得准。关键条件是 N 远大于 K。

为什么不是“直接用重排模型检索全库”？因为交叉编码器对每个 (查询, 文档) 对都要跑一次前向，而双编码器可以离线把文档向量全部算好。把重排模型用在百万文档上，就只剩暴搜一条路，延迟无法接受。两阶段是精度与延迟的交换：用便宜的第一阶段把候选从百万压到百，再让昂贵的第二阶段只处理这一百。

MECHANISM / CONTRAST

双编码器 vs 交叉编码器

重排序之所以更准，关键在于模型看输入的方式变了：粗排的双编码器（bi-encoder）把查询与文档分成两侧、各自编码，只在最后比一下向量；精排的交叉编码器（cross-encoder）把查询与文档拼接成一段文本，送入同一个编码器，让两个文本的每个词直接发生注意力，最后输出一个分数。

维度双编码器交叉编码器
输入方式查询、文档分别编码查询与文档拼接后一起编码
交互无（仅最后对比向量）深度交互（注意力跨越两个文本）
能否预计算文档向量可离线算好不可，每个候选都要一次前向
在线开销1 次查询编码 + 向量比对O(N) 次前向（N 为候选数）
典型用途第一阶段粗排第二阶段精排

这里需要澄清一个常见的误解：“交叉”指的是查询与文档拼接后共同编码，而不是两座塔共享权重。双编码器是否共享查询端与文档端的权重是一种设计选择；交叉编码器则是结构性质不同——它没有独立的两侧向量可以拿来预先建索引。

MECHANISM / COST

交叉编码器的代价

两种结构可以用两个式子对照。双编码器的分数是两个独立向量的点积，文档向量与查询无关，因此可以离线预计算；交叉编码器的分数是查询与文档拼接后过一起模型的输出：

s(q,d)=fθ([q;d])

右边依赖具体的文档 d，而且必须让模型看到整段拼接文本，所以无法提前把任何东西算好缓存。对 N 个候选就要做 N 次前向；这是纯增的计算量，不能被“聪明地索引”绕开。正因如此，交叉编码器才只用在候选很少的第二阶段。

批处理降的是延迟，不是计算量。把 N 个 (查询, 文档) 对打包成一个 batch 送进模型，能利用硬件的并行能力把墙上时间从“逐条相加”降到接近“一次前向”，但它们仍然各自算了一次。batch 大小受显存限制，设得过大反而会拉长单次延迟；具体数值应在自己的模型与硬件上实测，而不是照搬常数。

顺带一提，还有介于两者之间的第三条路线：让每个文档保留多个词向量、查询词与文档词做晚交互（late interaction，如 ColBERT）。它有预计算的余地，又比单向量保留更多细粒度信息，代价是存储与计算更重——它和交叉编码器不是一个方法，不能混为一谈。

MECHANISM / ENGINEERING

重排模型的选型

重排模型分两大类：可自己部署的开源交叉编码器，和托管的重排 API。选择时真正要问的是：数据能不能出域、有没有 GPU、要不要多语言、许可是否允许商用。

MECHANISM / EXPERIMENT

纯 Python 玩具重排器

下例不调用任何模型，用两个手写特征模拟“粗排顺序错了、精排把它纠回来”：特征一是整体字面重合（近似粗排信号），特征二是查询的两个关键实体是否同时出现（近似交叉编码器能看到的交互）。它不是神经网络交叉编码器，也不能证明“重排一定更好”，只用于说明重排“重排的是顺序、不改变候选集合”。

QUERY = "苹果公司2026年财务状况"

# 假设第一阶段粗排后的顺序（它把主题相关但没财务信息的文档排在了前面）
coarse = [
    "苹果公司的发展历史可以追溯到1976年",
    "2026年全球科技公司财务概览",
    "苹果公司2026年财务报告与利润披露",
    "香蕉的种植与营养价值",
]

def char_overlap(q, d):
    qs = set(q)
    return len(qs & set(d)) / len(qs)

def has_all(d, terms):
    return 1.0 if all(t in d for t in terms) else 0.0

def rerank(docs):
    def score(d):
        return char_overlap(QUERY, d) + has_all(d, ["苹果", "财务"])
    return sorted(docs, key=score, reverse=True)

print("重排后：")
for d in rerank(coarse):
    print("  ", d)
# 预期：同时命中主题与财务的文档从第 3 位升到第 1 位：
#   苹果公司2026年财务报告与利润披露
#   2026年全球科技公司财务概览
#   苹果公司的发展历史可以追溯到1976年
#   香蕉的种植与营养价值

运行条件：Python 3.10+，无第三方依赖、无网络。这里的特征是人为设定的启发式，与真实交叉编码器的学习特征不同；真实重排需要加载模型、对每个候选做一次前向，并消耗算力。

重排只改变候选的顺序，不改变候选集合。

MECHANISM / FAILURES

失败边界与评估

重排把一部分工作任务交给了模型，但不能把生成质量全部托付给它。以下几类失败在工程中反复出现。

失败模式表现应对方向
“相关”不等于“有用”泛泛的概述文档几乎与任何查询都相关，总被排在最前按“能否帮助回答”标注训练，或重排后加信息密度过滤
第一阶段漏召回正确文档根本不在 Top-N 里提高 N 或改粗排；重排无法补救没召回的文档
延迟失控N 太大或 batch 太小调 N、批处理、或换更小的重排模型
评估错位只看 Top-1 是否命中在同一标注集上比 recall@k / nDCG

第一类失败值得展开：重排模型的训练目标通常是相关性（relevance）——“这段文本和查询是不是在说同一件事”；而用户要的是有用性（usefulness）——“这段文本能不能帮我回答问题”。概述、目录、导航类文本与任何查询都高度相关，因此很容易占据前排。这是实践中的常见现象，不是某个基准上的测量；缓解方式是按“能否回答”重新定义训练标签，或在重排后按信息密度再过滤。

评估必须与上线一致。比较重排方案时，要固定分词、嵌入模型、索引版本与候选深度 N，只改变重排模型，否则差异无法归因。重排提升的是“前几名里正确文档的占比”，不是“答案一定正确”；检索再准，生成仍可能误用证据。

至此，检索链路的“粗排 → 融合 → 精排”已完整。但它们都假设用户的查询本身是清楚、可检索的。下一篇转向查询端：当用户的问题太短、太多口语、或本身就有歧义时，系统如何在检索之前先把查询改好。
