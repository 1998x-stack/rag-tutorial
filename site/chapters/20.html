GRAPH / RETRIEVAL

GraphRAG 与知识图谱：
当“相似”不够用

向量检索把“像不像”算得很准，却答不了“谁同时满足三个条件”。这一篇从向量检索的四个盲点讲起，说明知识图谱如何用实体-关系表示补上关系推理，Microsoft GraphRAG 的层级社区如何回答“整体趋势”这类问题，以及为什么图与向量应当互补使用。

MECHANISM / PROBLEM

向量检索的盲点

第九章到第十一章反复用到同一个直觉：向量检索擅长找“相似”的内容。但“相似”不等于“相关”。一个很常见的误解是“只要嵌入模型够好，向量检索就能回答任何问题”。下面这个构造的例子就能说明为什么不行。

假设一个内部知识库里搜索：“哪些员工同时参与过项目 Alpha 和项目 Beta？”向量检索会返回一批“和项目 Alpha 相关”的文档，再加一批“和项目 Beta 相关”的文档。但“同时参与”这个关系并不存在于任何单篇文档的向量里——它需要把两个集合取交集。向量相似度只会排序，不会做集合运算。

这是机制层面的局限，不是选型问题。换一个更强的嵌入模型、把 top-k 调大，都不能让“相似度排序”自动获得“关系推理”。前者回答的是“哪几个东西长得像我的查询”，后者回答的是“哪些对象满足一组结构化的条件”。

把向量检索容易失手的查询归成四类，后面会逐条说明图谱怎么补：

  • 全局性问题：“总结各团队近几年的主要风险”——答案需要多次聚合，而不是找到某一篇最像的文档。
  • 多跳推理：“A 与 B 合作的项目的负责人是谁”——要从 A 找到项目，再从项目找到负责人，跨了两次链接。
  • 精确匹配：“某季度的营收是多少”——相似检索会给回“相关财务讨论”，但不是那个数。
  • 关系理解：“同时参与两个项目的人”——需要的是“同时”这个集合条件，而不是语义相似。

知识图谱正是为了补上最后这一类而引入 RAG 的：它把知识写成实体与关系，让“关系”变成可被查询的对象。

MECHANISM / KNOWLEDGE GRAPH

从文本到知识图谱

把非结构化文档变成知识图谱，核心是把文本里的事实写成三元组：（实体，关系，实体）。例如从一句“张明参与了项目 Alpha”里抽出 (张明, PARTICIPATES_IN, Alpha)。这些三元组把“关系”从模糊的语义相似度里解放出来，变成可以被精确查询的边。

常见的构建流程共五步：

  1. 文档分块：和传统 RAG 一样，先把文档切成可处理的块。
  2. 实体抽取：从每个块里识别命名实体——人、组织、地点、项目、产品、日期等。
  3. 关系抽取：识别实体之间的语义关系（隶属于、参与、位于、导致等）。
  4. 实体消解（共指）：把不同文档里指向同一对象的名称统一，例如“苹果公司”与“Apple Inc.”。
  5. 图谱存储：把实体与关系写入图数据库（如 Neo4j）供查询。

实体与关系抽取现在常用 LLM 完成，但抽取本身是有损的：模型会漏、会错，实体消解也很难做到百分之百。因此图谱的“覆盖度”与“准确度”必须当作独立指标来评估，而不是假定它天然正确。

有了图，就能用图查询语言直接表达集合与多跳。下面是一段 Cypher（Neo4j 的查询语言），找出“同时参与多个项目”的员工：

// Cypher：找出同时参与多个项目的员工，并按参与项目数排序
MATCH (e:Employee)-[:PARTICIPATES_IN]->(p:Project)
MATCH (e)-[:PARTICIPATES_IN]->(p2:Project)
WHERE p.name <> p2.name
RETURN e.name AS employee,
       collect(DISTINCT p.name) AS projects,
       count(DISTINCT p) + count(DISTINCT p2) AS project_count
ORDER BY project_count DESC
LIMIT 10

WHERE p.name <> p2.name 是“两个不同项目”的集合条件——这正是向量相似度无法表达的部分。上面的查询仅为语法示例，它能否给出结果完全取决于图中有没有对应节点与边。

在一组三元组上做集合交集，找出同时参与两个项目的人。

MECHANISM / GRAPH RAG

层级社区与全局问题

有了图还不够，因为“总结公司主要风险”这类全局性问题不是排序题。微软研究院的 GraphRAG（Edge 等，2024）给出的思路是把索引做成多层结构：

索引阶段包含四层：实体与关系（原子事实）→ 社区检测（用图算法把紧密关联的实体聚成社区）→ 社区摘要（每个社区用 LLM 写一段描述）→ 全局结构（多层摘要组成可检索的层次）。社区检测常用的 Leiden 算法（Traag 等，2019）能在图上找到模块度较高的划分。

查询阶段因此有了两条路：局部搜索沿着某个实体附近的节点与边取证据，适合具体事实；全局搜索在高层的社区摘要上做映射-归约（分别让模型对每段摘要给出要点，再汇总），适合“整体趋势、主要主题”这类需要聚合的问题。这就是 GraphRAG 相对纯向量检索的差异：它不是把 top-k 换大，而是为全局问题另建了一条自下而上的聚合通道。

区分论文方法与后续变体。“实体抽取 + 社区检测 + 社区摘要 + 全局映射-归约”是上述论文提出的方法；社区检测的具体算法、层次数、摘要模型都可以替换。这些是实现选择，不要当成方法不可变的一部分。

MECHANISM / COMPARISON

图与向量：互补而非替代

一个常见的误解是“GraphRAG 要取代向量检索”。实际上两者回答的是不同形状的问题，互为补充：向量检索擅长“找出和目标最像的一大堆内容”，图谱检索擅长“找出满足一组关系条件的对象”。

维度向量 RAG图谱 RAG
检索机制语义相似度排序图遍历 + 关系匹配
擅长的查询开放式、探索性、找相似内容精确、结构化、多跳、全局聚合
全局性问题弱（只能给回局部片段）强（社区摘要 + 映射-归约）
多跳推理弱（跨文档链接困难）强（沿边遍历）
构建成本低（一遍嵌入）高（多步 LLM 抽取与摘要）
更新成本低（可增量嵌入）高（新事实可能影响社区划分）
主要风险“相似不等于相关”，漏掉关系条件抽取错漏、实体消解错、图谱覆盖不全

表格里的“强/弱/高/低”是定性比较，不是实测数值。到底哪个更适合，取决于你的查询里有多少比例属于多跳与全局问题——这必须用自己的查询日志去统计。

不要相信未经测量的“提升百分比”。原站页面里“混合架构整体准确率高出 15–30%”“百万文档单次构建 5000–20000 美元”等数字没有可核对的出处，本页已删除。图谱的构建成本确实高于向量索引，但具体贵多少，必须在自己的数据与模型上实测。

MECHANISM / ROUTING

查询路由与混合架构

既然两者互补，工业上常见的做法不是二选一，而是先判断查询类型，再选检索通道，最后把两路结果融合后交给生成模型。判断这一步通常由一个查询分类器完成，它把问题分成几类：

查询类型例子首选通道
事实型“X 产品的保修期是多久？”向量检索（甚至关键词）
关系型 / 多跳“同时参与两个项目的人是谁？”图查询
全局型“主要风险有哪些？”社区摘要 + 映射-归约
探索型“给我讲讲这个主题”向量检索 + 图谱补充

“查询分类器”是实现选择，不是方法的必需组件；它本身也会错分，因此需要与检索质量分开评估。另一个现实约束是成本：向量索引只需对文档做一遍嵌入，而图谱构建要对每篇文档做多步 LLM 调用（抽取 + 摘要），更新时还可能触发重新分社区。所以更常见的起点是“先用向量 RAG 打底，只对高价值的关系型/全局型查询加图谱通道”。

把失败情形与根因对照起来，更好定位问题：

现象可能的根因
图里根本查不到某个事实抽取阶段漏了；或该事实未被写入图
同一实体被当成两个实体消解（共指）没做好
社区摘要与具体事实矛盾摘要阶段失真；或底层抽取本身有错
全局回答笼统、没有细节只用高层摘要，没有下钻到实体证据
更新后回答变差新文档进了向量库但未更新图谱，两边不同步
图谱质量 = 抽取质量 × 消解质量。图上的推理再精确，也只能在“图里已有的边”上成立。把抽取的查全率/查准率与实体消解的正确率当作独立指标评估，不要假定图是“干净的真值”。

掌握了两条检索通道，下一步是把“是否检索、怎样拆解问题”本身也交给模型决定——这是下一章 Agentic RAG 的主题。
