PRIVACY / ACCESS CONTROL

数据隐私与访问控制：
让检索只看得见该看的

检索器天生追求“把最相关的东西都找出来”，而企业的权限体系追求“只给该看的人看”。这两个目标在 RAG 里正面相撞。这一篇解释权限应该在哪一层生效、隔离该怎么做、过滤放在检索前还是检索后，以及为什么“删除数据”还必须连向量一起删。

MECHANISM / PROBLEM

相关性与最小权限的冲突

向量检索的默认行为是：不管你是谁，把“最相关”的分块找出来。它不知道也不关心权限。而企业的安全原则是最小权限（principle of least privilege）：只给用户完成工作所需的最小访问范围。两者的目标恰恰相反——一个要“尽量都找出来”，一个要“尽量少给看”。

这个冲突在 RAG 里会被放大，因为有两个容易踩的坑：

  • 检索单元是分块，不是整篇文档。同一份文档里可能既有能对外公开的内容，也有内部数据。用“整篇可见/不可见”来做控制，要么泄露，要么把大量可用信息一并屏蔽。
  • 不能等生成时才过滤。如果不可见的分块已经进入上下文，模型可能把它写进回答、也可能被后续追问套出来。敏感内容一旦进了上下文，就难以“收回来”。
权限必须在检索层生效。正确的立场是：在把候选送给生成之前，就使不可见的分块根本不出现在结果里。这不是“多加一道检查”，而是把权限作为一种检索约束。以下各节把粒度、隔离方式与实现手段拆开看。

MECHANISM / MODELS

访问控制模型：四种粒度

从粗到细，常见的四种模型各自适合不同场景：

模型做法优点局限
文档级（ACL）整篇可见或不可见简单、易实现、不易错粒度粗；混敏文档要么全泄要么全封
分块级每个分块单独标可见性粒度细，能只公开可公开部分标注与管理成本高
角色过滤按用户角色在检索后过滤开发成本低后过滤可能使召回变少（下节展开）
属性控制（ABAC）由用户/资源/环境属性动态判定最灵活，能表达复杂策略策略复杂、难调试与审计

下面用一张“分块 × 角色”的可见性矩阵把问题说清楚：同一份文档的不同分块可以有不同的可见范围，这是文档级控制做不到的。

粒度越细，治理成本越高。分块级与 ABAC 能表达更精确的策略，但也意味着每个分块都要有可靠的标签、每套策略都要能被审计。选择粒度时，先问“最坏情况下泄露什么”，再决定投入多少标注与策略管理。

MECHANISM / ISOLATION

物理隔离与逻辑隔离

在多租户（多个客户/组织共用一个系统）场景里，第一个架构决策是：租户数据是“各存各的库”还是“混在一起靠字段隔开”。向量库通常提供两种思路：物理隔离（每个租户独立的集合/实例）与逻辑隔离（共享集合，用租户 ID 之类的字段过滤）。

维度物理隔离逻辑隔离
架构每租户独立集合/实例共享集合 + 过滤字段
隔离强度高（不依赖过滤逻辑）中（安全取决于过滤是否严密）
运维成本随租户数线性上升低（一套实例服务多租户）
资源效率低（每实例需预留）高（池化共享）
延迟表现可预测受“吵闹邻居”影响
适用强合规行业（金融、医疗）SaaS、企业内部多部门

两者并不是非此即彼。一个常见的折中是分区/命名空间：同一套集群，但每个租户落在独立的物理分区里，既保留比纯逻辑过滤更强的隔离，又不至于每租户一个实例。无论选哪种，“租户 ID”都必须作为过滤的必要条件，而不能假设检索器会自动隔离。

逻辑隔离的“高安全性”是脆弱的。只要有一处查询忘了带租户过滤，就可能跨租户泄露。因此逻辑隔离必须配合：默认拒绝（不带租户条件就不返回）、集中式过滤构造（不让业务代码手写条件）、以及回归测试（专门测“忘了过滤”会不会出事）。

MECHANISM / FILTERING

检索过滤：前过滤与后过滤

把权限变成检索约束，有两种时机，效果差别很大。

  • 后过滤（post-filter）：先做常规的近似最近邻（ANN）检索取 top-k，再按权限把不可见的丢掉。实现简单，但有个陷阱：ANN 是在整个向量空间里找最近邻，它不知道权限，很可能把大量不可见文档排在前面；过滤完之后，剩下的可用结果就不足 k 条。这就是“后过滤导致召回塌缩”。
  • 前过滤（pre-filter）：先把权限下推为检索条件，只在可见集合里做检索。结果都是可用的，但过滤后候选集变小，某些 ANN 索引的效率与准确度会受影响。

常见的折中是过采样后过滤：先取 k × m 条（m 比如 2～3），过滤后再截到 k。它比“取 k 再过滤”稳，但仍无法完全避免“不可见文档在前”导致的坍缩。多数向量库提供带元数据过滤的检索接口（filtered search），把它们用起来比在应用层手动后过滤更可靠。

过滤条件必须由权限系统生成，而不是手写。把“用户 → 过滤条件”的构造集中到一个地方，默认拒绝（无可见范围就不返回），可以避免“某个接口忘了加条件”这类致命疏漏。

MECHANISM / AUDIT

审计日志与删除义务

访问控制是否真的生效，不能只靠“代码看起来对”，而要靠可审计的证据。日志管理的基本实践建议记录完整的访问事件（NIST SP 800-92 对此有系统阐述）。对 RAG 来说，一条有用的审计记录至少应包含：

  • 是谁：用户标识、角色、所属组织/部门。
  • 访问了什么：查询、最终引用的文档/分块 ID 列表、以及被权限拦下的候选。
  • 何时/何地：时间戳、来源 IP / 客户端。
  • 为何可见：本次检索用的权限过滤条件与判定依据，便于事后复现。

日志要“用得上”，而不只是“存下来”。常见的用法是异常检测：同一用户短时间内大量访问与其职责无关的文档、或某敏感文档被不同角色的用户集中访问，都应能触发告警。

在处理个人数据时，还会遇到一个 RAG 特有的问题：删除不等于删掉原文。

义务（GDPR 举例）对 RAG 的含义
数据最小化（第 5 条）只索引入库必要的内容；嵌入前先去掉可逆的个人信息
删除权 / 被遗忘权（第 17 条）删除原文的同时，必须删除对应的向量与索引条目，否则旧数据仍可能被检索出来
数据可移植性（第 20 条）能导出与个人相关的数据，包括索引与检索痕迹
处理活动记录（第 30 条）记录索引了哪些数据、用了哪些模型、保留多久
“向量的遗忘”是最容易被漏掉的一步。很多团队删了原文，却忘了向量库里还留着指向它的嵌入与元数据，于是那个人的信息仍会被检索到。删除流程必须把原始文本、向量、元数据与缓存一并处理，并验证删除后确实检索不到。合规细节因行业与地区而异，请以官方法条为准并咨询法务。

MECHANISM / EXPERIMENT

纯 Python 演示：密级过滤

下面用最简的形式把“按密级可见”写成一段可计算的过滤。它用的是“密级”这种线性单调的简化模型（更复杂的 ABAC 需要多维属性，不能用一行比较表达）。

# 基于密级的权限过滤：只用标准库
LEVELS = ["public", "internal", "confidential", "secret"]

docs = [
    {"id": "c1", "clearance": "public"},
    {"id": "c2", "clearance": "internal"},
    {"id": "c3", "clearance": "confidential"},
]

def visible(docs, user_clearance):
    level = LEVELS.index(user_clearance)
    return [d["id"] for d in docs
            if LEVELS.index(d["clearance"]) <= level]

print("外部访客(public)  可见:", visible(docs, "public"))
print("内部员工(internal) 可见:", visible(docs, "internal"))
print("管理员(secret)    可见:", visible(docs, "secret"))
# 预期输出：
# 外部访客(public)  可见: ['c1']
# 内部员工(internal) 可见: ['c1', 'c2']
# 管理员(secret)    可见: ['c1', 'c2', 'c3']

运行条件：Python 3.10+，无第三方依赖、无网络。它只用一行比较做了“默认拒绝”的密级过滤（不可见的根本不出现在列表里）；真实系统里，用户的密级应从 IAM 获取，过滤条件应由权限服务集中生成，并下推到检索层而不是只在应用层后过滤。

不同密级的用户，看到的分块列表不同。

MECHANISM / FAILURES

失败边界与设计原则

访问控制做错时，后果往往不是“不准确”，而是“泄露”。下面是最常见的几类失败：

失败模式表现应对方向
后过滤召回塌缩过滤后可用结果不足 k前过滤 / 过采样后过滤
忘了带权限条件某个接口跨租户/跨密级返回集中式过滤构造 + 默认拒绝 + 回归测试
生成阶段才过滤敏感分块已进上下文，可能被写出把权限约束放在检索层
权限缓存过期转岗/离职后仍看得到旧数据周期性权限重认证、缩短缓存
元数据标签错机密内容被标成 public入库前校验、抽样审计
删除不彻底原文删了、向量还在删除流程覆盖文本+向量+元数据+缓存

把上面的处理汇总成几条可以逐条检查的原则：

默认拒绝

没有明确授权就不可见；漏配时的默认行为是“不给”，而不是“给”。

检索层生效

权限作为检索约束，而不是生成后的补救；不可见的内容不进上下文。

集中构造过滤

由权限服务统一生成过滤条件，不让业务代码手写，降低漏配风险。

可审计与可删除

留下能复现判定的日志；删除时连向量一起处理并验证。

没有“足够安全”这个终点。权限体系会随组织变化而腐化：新人、转岗、离职、并购都会让旧策略失效。因此访问控制需要定期重认证与红队测试，而不是“部署完就不管”。隐私与合规的具体要求因行业与地区而异，请以官方文本为准。

到这里，检索、生成与安全都已经就绪。但要回答“这套系统到底好不好”，还得有一把尺子——如何系统性地评估检索与生成的质量，是下一章 RAG 评估体系的主题。
