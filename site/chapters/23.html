FRAMEWORKS / DECISION

框架如何选：
LangChain、LlamaIndex 与“都不用”

“到底选哪个框架”在社区里吵得最热，但这个问题本身容易问错：两者其实处在不同层。这一篇不比较谁的教程多，而是先把定位、核心抽象与迁移成本讲清，再讨论什么时候用框架、什么时候直接用底层 SDK、甚至两个都不用。

MECHANISM / PROBLEM

选型问题容易问错

社区里最常见的问题形式是“LangChain 和 LlamaIndex 到底选哪个”。它默认两者是同一类工具、只能二选一。但一个更准确的问法是：我到底在买哪一层的抽象？如果把两者当成同一层的竞争品，就会得到一个“选谁都行、选谁都坑”的结论。

另一个常见误解是“框架只看功能多不多”。实际上，真正的成本在迁移与耦合：一旦你的数据接入、分块、索引逻辑都粘在某个框架的抽象上，换框架（甚至只是想绕过它的某个默认行为）都要重写。功能列表上的差别可以随时追上，粘在抽象上的成本不会自己消失。

框架的更新非常快，具体版本与 API 变化频繁。所以本页不比较“谁有多少集成、多少种分块器”这类随时会变的数字，而是把重点放在相对稳定的定位与抽象边界上。具体 API、支持矩阵与版本差异，请以各自官方文档为准。
不引用未经核实的案例数字。原站页面里“某创业公司数据索引代码占维护工作 60% 以上”“省下三个月”之类的叙述无法核对，本页已删除。选型教训应该来自你自己项目里可度量的维护成本，而不是一个虚构的故事。

MECHANISM / POSITIONING

两个框架的定位

两个框架都做过 RAG，但重心不同：

  • LangChain：一个通用的 LLM 应用框架，核心抽象围绕链（Chain）与代理（Agent）展开，目标是“用 LLM 构建任意类型的应用”，RAG 只是其中一个场景。
  • LlamaIndex：一个以数据为中心的框架，核心抽象围绕索引（Index）、检索器（Retriever）与查询引擎（QueryEngine），目标是把数据高效地接到模型上。

换句话说，这不是“两个同层框架选一个”，而是“你的重心在哪一层”。一个常见的组合是：用一遍底层库（如向量数据库的官方 SDK）直接把索引层做稳，再用一个编排层去组织多步流程。到底选谁，取决于你更缺“数据接得顺”还是“控制流编得顺”。

也要注意：框架的抽象命名随版本变化较快（例如“代理”“链”等概念都经历过重组）。所以本页只强调相对稳定的分工关系，不追具体的类名与 API。

MECHANISM / ABSTRACTIONS

抽象与迁移成本

框架的价值在于把重复的管道代码封成抽象；代价是这些抽象会渗进你的代码。评估一个框架，关键不是“它能不能做”，而是“它藏掉了什么、哪些东西又泄漏出来了”。

抽象藏掉了什么泄漏 / 耦合风险
数据加载器不同格式的读取细节格式支持不全时需自己写；行为随版本变
分块器切分策略的细节默认参数不一定适合你的文档（见第五章）
索引与存储向量库与嵌入的对接更换向量库或嵌入模型时可能要改代码
检索器 / 查询引擎检索与重排的编排想要自定义融合（如 RRF）时可能绕不开
链 / 代理控制流与工具调用调试时要穿透多层封装

降低耦合的一个通用做法：把检索层封在自己的接口后面。上层只调用你自己的 retrieve(query)，底下用哪个框架、哪个向量库都可以换。这样框架的升级或替换就不会渗透到业务代码里。

重写一遍检索逻辑是常见的隐藏成本。上一页图里的“重叠区”最容易重复建设：同一个检索逻辑在编排层和数据层各写一份，后期改一处忘了另一处，维护成本翻倍。先把接口定清楚，再填实现。

MECHANISM / PIPELINE

数据管线与编排

不管用哪个框架，RAG 的离线管线本质不变（第四到第八章已经讲过）：加载 → 解析 → 分块 → 嵌入 → 建索引，在线则是检索 → 重排 → 组装上下文 → 生成。框架把这几步封成上一节那几层抽象，并不会改变管线本身。

两者的接口风格差异，可以用两段接口示意来直观感受。下面两段都不是可直接运行的代码：它们依赖第三方库，且真实使用还需要配置模型凭证，所以本节不把它们当作可重现示例。

# 接口示意（需第三方库与模型凭证；本节不运行）—— 编排中心风格
# 概念形态，非真实 API；以官方文档为准
docs   = loader.load(source)             # 加载
docs   = splitter.split(docs, size=512)  # 分块
store  = vector_store.from(docs)         # 建索引
hits   = retriever.search(query, k=5)    # 检索
answer = chain.run(query, context=hits)  # 编排 + 生成
# 接口示意（需第三方库与模型凭证；本节不运行）—— 数据中心风格
# 概念形态，非真实 API；以官方文档为准
docs   = reader.load_data(source)        # 加载
docs   = parser(docs, size=512)          # 分块
index  = index.from_documents(docs)      # 建索引
engine = index.as_query_engine(k=5)      # 检索 + 生成
answer = engine.query(query)             # 一步到位

可以看到：一个把“检索”与“生成”显式分开，给你更多控制点；另一个把检索与生成包进一个查询引擎，入口更少。两者能达成的最终效果没有本质差别，差别在你需要在哪一步插手。

不要把接口示意当真实用法。上面两段是概念对比，参数名、类名与调用方式随时可能变，不要照着写进生产代码。实际接入请跟随对应版本的官方文档与示例。

MECHANISM / DECISION

什么时候都不用框架

“用框架还是自建”和“用哪个框架”是两个独立问题。自建听起来费力，但对一批场景反而更划算：

适合用框架

  • 还在快速原型阶段，需要快速跑通多种数据源与模型。
  • 管线是标准形态，框架的默认行为刚好契合。
  • 团队熟悉框架，能接受它的抽象与升级节律。

适合直接用底层

  • 范围小且稳定：只有少数文档源与固定的检索逻辑。
  • 需要精确控制检索 / 融合口径（如自实现 RRF）。
  • 有严格的依赖或供应链约束，不想引入大依赖树。
  • 团队更愿意少一层封装、少一层调试。

一个常见的中庸方案是：索引层用向量数据库的官方 SDK 直接做稳，编排层再按需要引入框架；或者反过来，先用框架跑通，再逐步把最关键的检索段换成自己的实现。关键是先用第二章讲过的“召回与生成分开评估”确认系统真的变好，而不是因为换了框架就假定会变好。

选型不应以“教程数量”为准。教程多意味着上手快，但也意味着网上很多示例已经过时。把它当参考，不当依据。
