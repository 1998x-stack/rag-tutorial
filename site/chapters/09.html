RETRIEVAL / DENSE

稠密检索：
双编码器与语义向量

BM25 依赖共享的词项，读不懂“换个说法”的提问。这一篇解释稠密检索如何把查询与文档映射到同一表示空间，让没有共同词的文本也能彼此靠近，以及这种能力从何而来、又在哪里失灵。

语义匹配需求双编码器对比学习失败边界

MECHANISM / PROBLEM

没有共同词，怎么也能找到？

用户提问“感冒了该怎么办”，而知识库里只有一段“上呼吸道感染的治疗方案”。两段文字里几乎没有相同的字词，BM25 无论怎么调参都召不回它——因为倒排索引里根本没有可匹配的词项。但人一眼就能看出这两件事在讲同一件事。

稠密检索（Dense Retrieval）要做的就是这种匹配：把查询和文档各自编码成一个固定维度的向量，让语义相近的文本在向量空间里彼此靠近。检索于是变成“找最近的向量”，即使两者没有共享任何词项。这与上一篇的稀疏检索恰好互补。

前提假设。稠密检索的有效性建立在两个假设上：编码器在训练中见过这类语义关系；查询与文档被映射到同一个可比对的表示空间。任何一个不成立，语义相近就不一定向量相近——这是后文失败模式的根源。

MECHANISM / ARCHITECTURE

双编码器：查询和文档各走一侧

把查询与文档送进同一个编码器、再比较输出的结构叫双编码器（bi-encoder）。它有两座“塔”：查询编码器 EQ 把查询编码成向量，文档编码器 EP 把段落编码成向量，然后计算两个向量的相似度。

DPR（Dense Passage Retriever，Karpukhin 等人 2020）就是代表性的双编码器：它用两个独立训练的 BERT 编码器分别处理问题和段落，并在训练目标上让相关问答对的向量靠近。需要澄清一个常见误解：查询端与文档端并不必须共享同一个编码器或权重。DPR 的查询编码器与文档编码器是分开的，共享与否是一种设计选择，不是定义上的强制要求。

双编码器真正的优势在于可预计算：文档向量可以在离线阶段全部算好并建索引，在线时只需编码一次查询，再与库里向量比相似度。代价是查询和文档在编码时彼此看不见，表达能力弱于让二者交叉注意的交叉编码器（cross-encoder）——后者更强但无法离线预计算，通常用于对少量候选做重排。

MECHANISM / TRAINING

对比学习与批内负样本

向量近不近，取决于编码器怎么被训练。稠密检索普遍用对比学习（contrastive learning）：对每个查询，准备一个相关的正例文档，以及一批不相关的负例；训练时把正例拉近、把负例推远。定义相似度为两个编码器输出的内积：

sim(q,p)=EQ(q)·EP(p)

负例的来源之一是批内负样本（in-batch negatives）：同一个 batch 里，其它查询的正例文档就当作当前查询的负例，不必额外挖负例。把 batch 内所有文档的相似度做 softmax，就是常见的对比损失：

L=−logexp(sim(q,p+))∑p∈batchexp(sim(q,p))

其中 p+ 是查询 q 的正例段落，分母遍历 batch 内所有被当作候选的段落。损失越小，正例在候选中的相对得分越高。这种“一个正例、多个负例”的形式与 Sentence-BERT 等句向量训练方法共享同一类思想（Reimers & Gurevych 2019）。

训练数据决定能力边界。编码器只学会区分它在训练中见过的语义关系。领域术语、行业黑话、新鲜事件若不在训练分布里，得到的向量就可能不把真正的同义文本摆在一起。这也是“换个开源模型就能解决领域检索”常常不成立的原因。

MECHANISM / METRIC

相似度：余弦、点积与距离

得到两个向量后，需要一个函数把它们比成一个分数。常见三种，语义各不相同：

度量是否受向量长度影响常见用法
余弦相似度否，只看方向文本相似度最常用
点积是，长向量得分大模型以点积训练时直接用
欧氏距离是，值越小越近部分聚类/近邻场景

两个向量的相似度通常定义为：

cos(q,p)=q·p∥q∥∥p∥
别混用不同模型的分数。当一个模型以点积为目标训练时，它的向量长度本身就携带信息；把它换成余弦，或与另一个模型的点积得分一起排序，都会改变结果。训练与检索必须使用同一种相似度，且向量必须来自同一模型、同一版本、同一归一化方式。不同模型的嵌入不在同一空间，它们的分数没有可比性。

MECHANISM / INTEGRATION

与 ANN 索引的衔接

稠密检索的在线开销，一次是“编码一个查询”，另一次是“在库里找最近邻”。把文档向量与查询向量直接暴力比较，正是上一篇讨论过的 O(n) 扫描；当库变大时，必须交给 HNSW、IVF 等 ANN 索引（见 第 07 篇）。因此一条完整的稠密检索链路是：离线用文档编码器预计算全部文档向量并建索引；在线用查询编码器编码一次，再让索引返回候选。

距离度量必须贯穿全链路。如果训练与评估都用归一化后的点积，而索引内却按原始欧氏距离建图与搜索，得到的候选就不是同一口径下的近邻。建库时就要把距离函数、归一化方式与索引参数一起记录进索引元数据，而不是事后补记。

这也解释了 ANN 与稠密检索为什么是两个独立的话题：ANN 只认“一堆向量加一个距离函数”，不关心向量是不是语义向量；嵌入质量与索引近似误差是两重独立的损失，评估时要分开定位。

MECHANISM / EXPERIMENT

纯 Python 的向量排序实验

下例不依赖任何模型，用人为指定的二维向量演示一个关键事实：同一种向量，换成不同相似度，排序会变。这不是学习得到的嵌入，只是几何演示。

import math

# 人为指定的二维“嵌入”：仅演示几何排序，不是模型输出
vec = {
    "Q":  [0.9, 0.4],   # 查询
    "D1": [1.0, 0.1],   # 方向与查询接近
    "D2": [3.0, 3.0],   # 方向略偏，但向量很长
    "D3": [-0.8, 0.6],  # 与查询方向相反
}

def norm(a):
    return math.sqrt(sum(x * x for x in a))

def cosine(a, b):
    return sum(x * y for x, y in zip(a, b)) / (norm(a) * norm(b))

q = vec["Q"]
for name in ("D1", "D2", "D3"):
    p = vec[name]
    print(name,
          "cos=", round(cosine(q, p), 3),
          "dot=", round(sum(x * y for x, y in zip(q, p)), 3))
# 预期：余弦排序 D1 > D2 > D3（看方向）；
#       点积排序 D2 > D1 > D3（长向量被抬高）。

运行条件：Python 3.10+，无第三方依赖、无网络。上述向量是手工选定的，目的是让两种度量的差异在几个小数位上可见；真实嵌入的维度通常是数百维，数值不可这样直观看待。实践结论只有一条：训练、建库、检索选用同一种相似度，并在索引元数据里记录归一化方式与模型版本。

同一组向量：余弦看方向，点积还看长度，两者排序可能不同。

MECHANISM / FAILURES

语义漂移与失败边界

稠密检索很强大，但它失败的地方往往很隐蔽，因为一个“看起来合理”的向量分数不会自己报警。

失败模式表现应对方向
领域不匹配同义术语的向量不靠近，语义匹配失效用领域数据微调编码器或补正负例
向量坍塌大量相似文档挤在一起，结果高度重复查多样性、去重，检查嵌入分布
长文档单向量细节被压缩掉，召回语义但漏掉关键句分块、多向量或段落级检索
模型/索引不一致换模型后旧向量仍在新库里被比较版本绑定，全量重嵌并重建索引
模型不能“换着用”。今天用 A 模型编码库，明天用 B 模型编码查询，即使两个模型都“很好”，它们也不在同一表示空间，分数毫无意义。固定一个模型版本编码，是稠密检索可复现的前提；频繁切换模型会引入无法定位的误差。

另外，评估稠密检索必须在同一标注集、同一模型角色（查询/文档侧用什么模型）、同一向量分数口径与同一索引版本下比较。公开榜单上的模型排名绑定于特定数据集与评测脚本，不能直接搬到你的语料上当作结论。很多看似“模型提升”的差异，其实来自分块方式、否定例或查询预处理的变化。

至此，稀疏与稠密两路都已具备。下一篇要处理的问题是：当两路召回各有长短时，系统怎么把它们的候选与分数合在一起，而不把两者的缺点也乘在一起。
