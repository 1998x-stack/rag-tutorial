CAPSTONE / PROBLEM

拼装技术 ≠ 好系统

常见的误解是“把前面学到的每个环节都接上，系统就会更好”。实际上，每接一个环节都会引入新参数、新依赖与新失败模式（见第二十七章）；没有可度量的基线，你无法判断某一步到底是帮助还是伤害。

设一个具体场景：某中型公司有数万份内部技术文档、产品手册与故障排查指南，分散在 Wiki、Confluence 与 PDF 中。目标是让工程师用自然语言提问，拿到带出处、可核查的答案。真正难的往往不是模型，而是：文档怎么解析、怎么分块、召回不准到底是哪一环出了问题。

不引用未经测量的提升。原页给出的“召回率 +15%”“检索精度 +22%”“成本降低 40%”“MTTR 从 2 小时降到 10 分钟”等数字没有可靠出处，本页已删除。这些只能在你自己的数据与系统上测。下文凡涉及数值处都标注为教学示意。

本章的叙事顺序是：先看完整流水线，再看入库与查询两侧，最后把“评估回路”作为驱动改进的主线。

CAPSTONE / ARCHITECTURE

一张图：完整流水线

把系统分成离线入库与在线查询两条路径，中间用共享索引相连，再用评估回路把两端连起来。入库是“一次做、长期用”，查询是“每次都要快”，两者的优化目标不同，必须在图上分开。

接下来先看入库侧，再看查询侧，最后展开评估回路。

CAPSTONE / INGESTION

数据管线：从摄入到入库

入库侧的目标是可追溯：每个可检索的分块都要能回答“它来自哪份文档、哪个位置、什么版本”。下面是一个最小骨架，用来对齐各章的职责划分，并非可直接运行的完整实现：

# 伪代码：入库管线骨架（parse / chunk / embed / index 需按项目替换为真实实现）
def ingest(docs):
    chunks = []
    for doc in docs:
        pages = parse(doc)                 # 第 04 章：保留阅读顺序与表格结构
        for ch in chunk(pages, size=512, overlap=64):   # 第 05 章：0 ≤ overlap < size
            chunks.append({"text": ch.text, "meta": ch.meta})  # meta 含来源/页码/版本
    vectors = embed([c["text"] for c in chunks])  # 第 06 章：查询与文档用同一模型与度量
    vector_index.add(vectors, chunks)    # 第 07 章：向量索引（HNSW / IVF）
    bm25_index.add(chunks)               # 第 08 章：倒排索引，供稀疏检索

上面是概念骨架，变量与函数均为占位符，不能直接运行；它只展示流程与各章职责。真实入库需处理去重、增量更新、失败重试与版本回滞。

  • 解析不等于抽取文本：PDF 的文字层不等于阅读顺序，表格需保留行列与单位（第 04 章）。
  • 分块按文档类型差异化：技术手册与 FAQ 的合适粒度不同，需分别验证（第 05 章）。
  • 模型角色要固定：查询端与文档端的向量必须相容，比较得分需固定模型与索引版本（第 06 章）。
  • 入库要能重跑：换模型或改分块后需重建索引，元数据与版本号让这件事可控。

CAPSTONE / SERVING

查询路径：从提问到带引用

在线侧的目标是在延迟预算内给出可核查的答案。它把第 10–15 章的环节串成一条链：

# 伪代码：查询路径骨架（各步为占位符）
def answer(query, role):
    if (hit := cache.get(query)):           # 第 27 章：语义缓存，未命中才继续
        return hit
    q = rewrite(query)                      # 第 09 章：改写为检索友好的形式
    dense = vector_index.search(embed(q), k=20)   # 第 07 章
    sparse = bm25_index.search(q, k=20)           # 第 08 章
    cands = rrf_fuse(dense, sparse)         # 第 10 章：融合两路排名
    top = rerank(q, cands, k=5)             # 第 11 章：交叉编码器重排
    ans = generate(q, top)                  # 第 13–14 章：组装上下文 + 带引用生成
    return {"answer": ans.text, "citations": ans.spans}  # 每条声明可回到原文

同样是概念骨架，不能直接运行。它只用来展示“哪一步用哪一章的方法”，以及每一步的输入输出。

引用是产品需求，不是装饰。工程师需要能点开出处核对。因此生成阶段就要把“哪句话引用了哪个分块”记录下来（第 14 章），而不是事后猜。

这条链上任何一步的参数都对结果有影响，所以下一步的评估必须能分步归因：是召回没拿到，还是重排没排好，还是生成没用资料。

CAPSTONE / EVALUATION

评估与持续优化

系统的上限由数据质量决定，但要把“感觉变好了”变成“可复现地变好了”，靠的是固定标注集 + 分步指标 + 基线对比。检索侧与生成侧要分开度量：

层次问题代表性指标
检索该召回的分块有没有进候选？Recall@k、context recall / precision
排序相关内容有没有排到前面？MRR、nDCG
生成答案是否忠于给定资料？faithfulness（基于资料的可支持性）
端到端回答是否切题、引用是否对得上？answer relevancy、人工抽查

指标的具体定义与计算方式需固定到具体工具与版本上，不同实现的同名指标未必可比。RAGAS 是一套常用的框架，它把 faithfulness、answer relevancy、context precision / recall 等拆成可自动计算的项（见下方来源）。

比较的前提。比较两个方案时，必须固定标注集、模型角色（查询/文档）、向量分与索引版本；否则差异可能来自混用了不兼容的模型或变了的基准，而不是你的改进。

CAPSTONE / LESSONS

经验教训：可迁移的原则

把原页那些带具体百分比的“经验值”换成可迁移的判断。下表的每一项都不依赖特定模型或数据量，但都需要你在自己的项目里验证：

领域常见坑可迁移的做法
分块对所有文档用同一 chunk_size按文档类型差异化分块，并在标注集上对比
嵌入用不适合目标语言的通用模型选与语种/领域匹配的模型，查询与文档端保持相容
检索只用单一索引稠密 + 稀疏混合，用 RRF 类方法融合
评估只看人工抽查或“感觉”建可复现的标注集 + 自动化指标 + 固定基线
缓存没有缓存或从不失效语义缓存 + 精确匹配两级，并随数据变更失效
可观测性出问题只能翻日志分阶段追踪与告警（见第二十五章）
“最佳实践”会过时。模型、索引与框架都在迭代，上面每条都要重新验证，不要当成永久正确的结论。

结语：从小处着手

这套课程从 RAG 的基本概念出发，走过文档解析、分块、嵌入、检索、重排、查询优化、上下文组装、引用溯源、幻觉检测、安全与隐私、评估、多模态、GraphRAG、Agentic、框架选型、向量数据库调优、可观测性，直到生产部署。最后一章把它们串成一条流水线。

给三条建议：

  • 先跑通，再优化。选一个熟悉的领域、拿一批文档，用一条简单但完整的管线跑通全流程，再引入评估回路逐步改进。
  • 数据优先。系统的上限由数据质量决定；数据清洗、分块与嵌入值得投入，但每一项都要用指标验证。
  • 持续学习，保持怀疑。技术迭代很快，今天的最优选型未必适用于半年后；把指标与基线保留下来，才能判断新方法是否真的更好。

第一个系统不完美是正常的。重要的是它可运行、可衡量，并且知道下一步该改哪里。
