OBSERVABILITY / DEBUGGING

RAG 调试与可观测性：
从“靠猜”到定位到阶段

RAG 不是一次调用，而是一条多阶段流水线。检索静默返回空结果、索引重建失败、嵌入模型换了版本——这些都可能只表现为“答案变差了”。没有指标、追踪与日志，你只能靠猜。这一篇讲清怎么把一次请求拆到各阶段，把质量退化变成可告警的信号。

三支柱追踪根因告警

MECHANISM / PROBLEM

没有可观测性只能靠猜

一个常见的错觉是“它在我机器上是对的”。RAG 是一条多阶段流水线（检索 → 重排 → 组装 → 生成），任何一段静默失败，对用户来说都只是“答案变差”——而你不会知道是哪一段。

举一个典型的静默失败：凌晨的索引重建因为磁盘空间不足而失败，在线查询仍然“成功”——因为调用没报错，只是检索返回了 0 条，生成模型拿到空上下文后照样生成一段流利的回答。整个链路都是绿的（调用成功），但答案是错的。如果有一个“检索结果数量”的监控，这个问题能很快被发现。

RAG 的失败往往是“能跑但错”，不是“报错”。所以只监控错误率是不够的。必须把检索结果条数、召回质量、引用完整度这类“语义层”的信号也纳进来——它们比 HTTP 状态码更能提前发现问题。
不引用未经证实的故障故事。原站页面里“某 SaaS 公司黑色星期四”“两小时才发现”等叙述无可靠出处，本页已删除；这里只保留机制描述。同样，本页不引用任何“各阶段典型耗时”的数字。

要分别回答“哪里慢了”和“哪里答错了”，需要三样东西：指标、追踪、日志。

MECHANISM / PILLARS

指标、追踪、日志

可观测性通常拆成三根支柱，各回答一个不同的问题：

  • 指标（Metrics）：聚合的数值信号——延迟分位、QPS、错误率、召回率、召回条数、token 消耗。回答“现在好不好”，用于趋势与告警。
  • 追踪（Traces）：一次请求从头到尾的完整链路，包含每一阶段的耗时与属性。回答“哪里慢了”，用于定位到具体阶段。
  • 日志（Logs）：各组件的事件明细。回答“为什么”，用于深度排查。

对 RAG 来说，第三类信号特别重要，因为它们是语义层的：检索返回了几条、重排后分数分布如何、生成里带了几条引用。它们不是 HTTP 层能给的，但恰恰是“能跑但错”类故障最早暴露的地方。

先打点再优化。没有基准数据时，任何“变慢 / 变差”都只能靠回忆。先把管线每段加上耗时与关键属性（结果条数、模型名、索引版本），才有后面的回归监控（见第十八章）。

MECHANISM / TRACE

把一次请求拆到各阶段

一次 RAG 请求包含多个阶段。用分布式追踪的标准（如 OpenTelemetry）可以把它们表示成一棵 span 树：每个阶段一个 span，记录起始时间、耗时与自定义属性。这样“总耗时高了”就能立刻回答成“哪一段高了”。

关键不只是“耗时”，而是每个 span 上带的语义属性。对每个阶段，值得记录的至少有：

阶段值得记的属性
查询改写（若有）原查询、改写后查询、是否走了改写
嵌入编码所用嵌入模型名与版本
检索返回条数、索引版本、top-k、是否带过滤
重排重排前后顺序变化、使用的模型
生成上下文里包含几条引用、输出 token 数

下面用一条玩具 trace 把“找最慢阶段”变成能跑的东西（纯标准库）：

# 从一条玩具 trace 里找最慢的阶段（纯标准库）
spans = [("query_rewrite", 210), ("embed", 90), ("retrieve", 25),
         ("rerank", 130), ("generate", 1200)]
total = sum(ms for _, ms in spans)
for name, ms in spans:
    print(f"{name:15s} {ms:5d}ms  {ms / total:6.1%}")
slowest = max(spans, key=lambda kv: kv[1])
print("最慢阶段:", slowest[0], "占总耗时", f"{slowest[1] / total:.1%}")
# 预期输出：
# query_rewrite     210ms   12.7%
# embed              90ms    5.4%
# retrieve           25ms    1.5%
# rerank            130ms    7.9%
# generate         1200ms   72.5%
# 最慢阶段: generate 占总耗时 72.5%

运行条件：Python 3.10+，无第三方依赖、无网络。它们只是人为指定的毫秒数，不是任何系统的实测；真实系统里这些耗时全靠追踪采集。

按阶段耗时占总耗时的比例，找出最慢的一段。

MECHANISM / ROOT CAUSE

故障与根因对照

可观测性的价值在于把“现象”映射到“环节”。下面是一些常见现象与可能根因的对照，它们分别对应前面各章讲过的机制：

现象可能的根因先看什么
回答变差，但检索看着还行生成阶段没用好好上下文，或提示改了固定召回结果，单独测生成
调用都“成功”但答案空泛检索返回 0 条（如索引重建失败、空索引）检索返回条数的指标 / span 属性
召回突然下降，没有代码变更嵌入模型或索引版本被换过（口径不一致）比对线上嵌入 / 索引版本与基准的版本
跨领域 / 跨语言误召回索引未按领域或语言隔离检索结果里的领域分布（第二十二章）
延迟突增某个阶段变慢（模型排队、索引碎片）那一分钟的 trace 瀑布
引用编号越界 / 不对应引用生成或组装阶段出错引用校验日志（第十四章）
区分“没检到”与“检到了没用好”。这是 RAG 排查里最关键的一刀。把检索结果与最终回答一起记录，才能知道该改检索还是改生成——否则很容易把生成的问题当成检索的问题（或相反）。

MECHANISM / ALERTING

监控什么、何时告警

把语义层信号接成告警，比只监控 HTTP 错误率更能早发现问题：

  • 硬性信号：检索返回 0 条的比例、引用校验失败率、超时率。这些能直接抓住“静默失败”。
  • 质量信号：用固定基准集定期跑召回 / 忠实度（第十八章），与基线对比，跌过阈值就告警。
  • 性能信号：各阶段耗时分位（P50/P95/P99）与吞吐；延迟告警应分阶段，而不是只看端到端。
  • 抽样回溯：定期抽样具体 trace，人看一遍检索到的上下文与引用是否合理。

把离线基准接进 CI/CD（第十八章），能让每次改动都自动“秤”一下；指标下降超过阈值就阻止合并。阈值本身是工程约定，需依业务容忍度设定，不存在通用定值。

告警要能落到具体请求。指标告诉你“变差了”，但要定位到“哪一条请求、哪一段 span、哪些检索结果”，就必须靠 trace 与日志的关联。三者用同一条 trace id 串起来，才能从指标一步跳到明细。

观测本身也要控成本：全量存每一条 trace 往往太贵，常见做法是采样 + 对异常请求全量保留。但采样会漏掉长尾问题，需与硬性信号（如零结果率）配合。
